## 2.1 指标精确定义:面试高频,且是压测的起点

先看一条请求的时间线:

```
t0 ──────────────────────────── t_first ──── ──── ──── t_end
|  排队 |      prefill | 首个decode | decode…decode |
|─────────────── TTFT ──────────────|── ITL ─ ITL ─ ITL ─|
|────────────────────── E2E ─────────────────────────────|
```

- t0:请求发出(到达引擎);t_first:收到首个输出 token;t_end:收到最后一个 token
- n_out:输出 token 数

四个核心指标的精确定义:

> **(2-1) TTFT = t_first − t0 = 排队等待 + prefill + 首个 decode 步**
>
> **(2-2) TPOT = (E2E − TTFT) / (n_out − 1)**
>
> **(2-3) ITL_i = t_i − t_{i−1}**(逐 token 时间序列,相邻两 token 各一个)
>
> **(2-4) E2E = t_end − t0**

三个易混淆点(面试追问常在这里):

1. **TTFT 是"请求级"指标,且包含排队等待**。所以 TTFT 分布 = 调度状态 + prefill 成本 + 首步延迟的混合,**不能读成"prefill 花了多久"**。要把排队 / prefill / decode 拆开,必须看服务端日志(vLLM `log_stats` 提供分段)——这是第 20 章 L2 组件拆解的数据基础。
2. **TPOT 是聚合值,ITL 是时间序列**。TPOT 会稀释尖刺:一次抢占重算可能造成某个 ITL 飙到 500ms,但输出 512 token 时 TPOT 几乎不动。**看长尾应该看 ITL 分布,而不是 TPOT**——这是第 22 章 p99 排查的第一课。
3. **TTFT 与 TPOT 测的是不同的物理量**:TTFT 主要由 排队 + prefill 决定(算力 + 调度),TPOT 主要由 decode 的 batch 状态决定(带宽 + 调度)。第 1 章的"两种形态"正好对应这两个指标——**优化 TTFT 和优化 TPOT 是两份不同的工作**,压测报告里混着谈是常见错误。

吞吐:

- 请求级:req/s(完成请求数 / 时间)
- token 级:系统吞吐 = 总输出 token / 总时间(tokens/s)

注意:**"吞吐"永远是负载曲线上的一个点**。"吞吐 5000 tokens/s"必须附带"并发 32 时"才有意义。曲线上有两个特殊点(2.5 节展开):

- **saturation 点**:吞吐不再随并发上升的并发
- **SLO knee 点**:SLO(Service Level Objective,服务水平目标,如"p95 TTFT < 2s 且 p95 TPOT < 50ms",与业务约定的延迟/质量约束)即将被违反的并发

goodput(本书的核心吞吐指标):

> **(2-5) goodput = SLO 约束下的最大可持续输出 tokens/s**

定义:给定 SLO(例:p95 TTFT < 2s 且 p95 TPOT < 50ms),逐步加压直到 SLO 被违反,取最后一个满足点处的吞吐。再往上就是"违反 SLO 的裸吞吐",没有业务意义——SLO 破了的第 4 个 percentile 和系统挂掉没有本质区别。**本书约定:不带 SLO 约束的"吞吐"一律视为不完整指标。**

分位数:

- p50 / p95 / p99:50% / 95% / 99% 的请求(或 token)低于该值
- **尾部才是真实 SLO**:p99 = 10s 意味着每 100 个用户有 1 个等 10 秒
- 健康度指标:**p99/p50 比值**。≈1-2 为健康;> 3 说明系统存在系统性长尾问题(第 22 章)。比值比绝对值有用——绝对值随模型 / 负载变,比值反映的是"系统自身的调度健康度"

> **案例框(示意数字):同一个模型,goodput 因 SLO 不同差 4 倍**
> 7B on 8×H100:定义 SLO 为 "p95 TPOT < 50ms" 时 goodput ≈ X;放宽到 "< 100ms" ≈ 2X;"无 SLO 压到饱和" ≈ 4X(此时 p99 TPOT > 500ms)。同一硬件、同一配置,三份压测报告"都正确",数字却差 4 倍——SLO 不固定,压测数字就不能用于容量规划。

## 2.2 负载模型:压测结果可信的前提

一次压测 = **到达过程 × prompt 分布 × 输出分布 × 前缀复用率**。四个变量任何一个没声明,结果都不可比。

**1. 到达过程**

- 固定 QPS:确定性,用于容量验证与 A/B 对比(其余全固定、只动一个变量)
- 泊松过程:逼近真实在线到达,生产容量测试的默认选择
- 突发(burst):模拟秒杀 / 活动(如 10× QPS 持续 10s),用于长尾与 shed(load shedding,过载时主动拒绝一小部分请求以保护多数请求,Ch22)测试(第 22 章)

**2. prompt 分布**

- 定长:最简,用于 kernel / 参数对比(第 25 章实验主力)
- 长度分布:真实 trace(ShareGPT、AzureLLM 开放 trace)带长尾,输入 1K-8K 常见,RAG 场景可到 100K+
- **前缀复用率**:0%(全随机)/ 50%(共享 system prompt + 不同用户内容)/ 高复用(RAG:固定 top-k 文档前缀)。这个变量能把 TTFT 差出一个量级(第 5 章前缀缓存)——**并发相同、复用率不同的两份报告不可比**

**3. 输出长度分布**

- 定长:decode 性能测试(第 25 章)
- 真实分布:写作类任务输出长、问答类短,常用对数正态近似
- 输出长度直接决定每请求的 decode 时长 → 决定 KV 占用时间与 batch 组成

**4. 压测报告的"三问"约定**

每份压测报告的负载定义段必须回答:**多少请求?什么分布(到达 × 输入 × 输出 × 复用率)?平均输出多长?** 答不出来,报告里的数字只是数字。

[进阶] 设计负载时还要问"这个负载压 SLO 的哪个分量":TTFT SLO → 长 prompt + 高并发;TPOT SLO → 高并发 + 长输出;goodput → 扫整条曲线(2.5)。

## 2.3 工具链:vLLM bench_serving / GenAI-Perf / LLMPerf

选型原则:先够用最熟悉的,指标口径一致比工具先进更重要。

- **vLLM `bench_serving`**(内置,本书实验默认):OpenAI 兼容协议;输出 TTFT / TPOT / ITL 分位数 + 吞吐;关键参数:`--num-prompts`、`--request-rate`(泊松 QPS)、`--dataset-name sharegpt`(真实 prompt 分布)、`--max-concurrency`
- **NVIDIA GenAI-Perf(benchmaker)**:完整的 SLO / goodput 指标体系、多机场景,NVIDIA 栈基线
- **MS LLMPerf**:goodput 为中心,多 provider

**客户端计时 vs 服务端日志(必须双轨)**:

- 客户端:含网络、网关、TLS——用户实际体感,正式报告的主口径
- 服务端(vLLM `log_stats`):引擎内部真实分段(排队 / prefill / decode)——辅助口径,用于拆解(第 20 章的基础)
- 两者差距大时,问题在网关 / 网络层——差距本身就是一个排查点,不要"取平均"

**warmup 与 cold start(两个用途,别混)**:

- warmup(应丢弃):前 N 个请求含引擎编译、CUDA graph 捕获(把一串 kernel 录成图一次提交,大幅降低每步 CPU launch 开销,Ch12 §12.3)、Triton JIT(Triton:开源 GPU kernel DSL,Python 风格写、JIT 编译到 PTX,Ch12)、前缀缓存冷启动——压测结论只基于 warmup 后数据
- cold start(是指标本身):扩容 / 重启后的第一个请求是真实线上场景(第 23 章),其 TTFT 单独统计,不混入稳态数据

**硬件状态固定(每次运行前检查并记录)**:

- `nvidia-smi`:power limit、clock、温度、共驻进程
- DCGM(Data Center GPU Manager,NVIDIA GPU 监控守护进程,SM Active/时钟/降频以字段 ID 暴露,Ch10 §10.4):throttle 原因(HW/SW Power、Thermal)
- 驱动 / CUDA / 框架版本(登记附录 G 版本基线)

## 2.4 常见坑(现象 → 误诊 → 正解)

1. **越压越慢(降频)**:持续高负载 → 功耗墙 → 降频。现象:前 100 请求快、后段慢,曲线"衰减"。误诊:模型或框架有问题。正解:监控 clock + `power limit`;提功耗上限,或承认稳态值——**线上稳态就是这个状态,压测必须压到稳态**。
2. **碎片未预热(冷显存池)**:冷进程下首批长请求被拒 / OOM,随后正常。现象:前期错误零星、后段干净。误诊:显存不够。正解:warmup + 预热负载;核对框架预分配(`gpu-memory-utilization`)。
3. **限流 / 重试污染数据**:客户端对 429 / 超时重试 → 单个"请求"时长跨多次尝试。现象:少数请求 TTFT 极端大。误诊:系统长尾。正解:重试单独统计,或用服务端日志(服务端不感知客户端重试)。
4. **客户端瓶颈**:单机客户端并发 1000,客户端自己发不动。现象:"吞吐"早饱和,但服务端 GPU 利用率还不高。正解:服务端日志交叉核对——服务端吞吐 > 客户端吞吐即客户端瓶颈,加客户端节点。
5. **输出长度漂移**:温度 / prompt 漂移使输出比预期长 → "吞吐"虚高、单请求延迟失控。现象:同 prompt 两次运行平均输出长度不同。正解:固定 seed + temperature=0,或在报告中记录实际输出长度分布。

> 五个坑的共性:压测测的是"系统",而系统包含 GPU 电源策略、显存池状态、客户端、网关。**除被测变量外,其余全部固定**——这是压测纪律的全部。

## 2.5 [进阶] SLO 约束的吞吐实验:找 goodput 曲线

步骤(可直接模板化成脚本):

1. 固定 SLO(例:p95 TTFT < 2s 且 p95 TPOT < 50ms)
2. 扫并发(或 QPS):1, 2, 4, 8, 16, 32, 64, 128;每点稳态 ≥ 60s,丢弃 warmup
3. 每点记录:p50/p95/p99(TTFT、TPOT)、系统吞吐、SLO 达标率
4. goodput = SLO 满足的最大并发处的吞吐(公式 2-5)
5. 画两条曲线:吞吐-并发、SLO 达标率-并发

**读曲线的三个点**:

- **knee 点**:SLO 达标率开始下跌的并发 = 容量规划点(第 3 章容量公式与第 23 章 autoscaling 的输入)
- **saturation 点**:吞吐曲线平台 = 裸容量上限("还能压多少"的参考)
- **两者间距**:knee 明显 < saturation → "还有容量但 SLO 先破了"→ 问题是**长尾不是容量**(转第 22 章);knee ≈ saturation → 容量问题(第 3、19 章)

> **案例框(合成,数字为示意):knee < saturation 是最容易误诊的场景**
> 某团队把并发压到吞吐平台,结论"到容量上限了,该买卡"。实际 knee 点在 saturation 的 60% 处:SLO 先被长 prefill 混入 decode batch 打碎(p95 TPOT 尖刺)。开 chunked prefill(第 6 章)后 knee 右移 ~40%——**没买卡,SLO 达标**。结论:先看 knee 与 saturation 的间距,再决定"买卡"还是"调调度"。

1. 部署 7B(vLLM,默认参数)

   - A:定长 input 512 / output 128,QPS=4(固定)
