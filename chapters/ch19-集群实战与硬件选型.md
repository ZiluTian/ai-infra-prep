## 19.1 硬件对比与 serving 影响(选型主表见附录 B)

| | H100 SXM | H200 SXM | B200 |
|---|---|---|---|
| HBM | 80GB,3.35TB/s | 141GB,4.8TB/s(+44%) | 180GB,7.7TB/s |
| 精度 | FP8 1979T | 同 H100 | FP8 ~4.5P / **FP4 ~9P** |
| NVLink | 900GB/s | 900GB/s | 1.8TB/s |

**对 serving 的传导(Ch10 结论的落地)**:

- **H100 → H200**:decode(memory-bound)预期 **+30-40%**(带宽 +44%,attention/计算段不受益,打折);prefill(compute-bound)≈ 不变;**KV 容量 +76% → 并发上限 +70-76%(Ch3 公式直接回代)**。一句话:"H200 买的是并发与长上下文,不是算力"
- **B200**:FP4 让 MoE 权重字节 1/4 → **单卡模型容量 ×4 + decode 带宽 ~2×(vs H100)**;代价 = 生态成熟度(FP4 kernel/量化工具链 2025 年仍在爬坡,Ch8 §8.5)
- **H800(常见变体)**:NVLink 降为 400GB/s → 节点内 TP 通信比上升(TP8 可用,但通信占比 ~2×)——**看拓扑表再谈 TP**(Ch18 §18.1)

**"该买什么卡"四步决策(面试模板)**:

```
① 容量:模型 + KV 池装不装得下?(Ch3 公式,先定最小卡数)
② 带宽:decode TPOT 目标 → 需要多少 HBM 带宽?(Ch1 roofline)
③ 价格:$/card-hour × 卡数 × 利用率(§19.4)
④ 生态:kernel 成熟度(FP4? MLA 特化 kernel? DeepEP 支持?)
```

典型结论:低延迟 chat → H200;高吞吐批处理 → H100(性价比)或 B200(FP4 MoE);1M 长上下文 → H200/B200(容量先行);MoE 大模型 → B200(FP4)或 H100 FP8(稳妥)。

## 19.2 集群形态与故障域

**基本单元**:8 卡 HGX 节点 + 8 个 NIC(GPU:NIC = 1:1,rail-optimized,Ch18 §18.2)。**节点 = 调度与故障的基本单位**——因为 gang 调度要求并行组整组分配(Ch14 §14.4):

- **1 节点挂 = 整个并行组挂**(TP/EP/CP 状态跨卡)→ 容量瞬间掉 1 个副本
- **TP8 组不能降级成 TP7**(切分不均)→ 恢复 = 换整节点重启,不是"补一张卡"
- **容量规划含义**:要维持 N 副本的 SLO,物理上需要 **N + 1 个整节点**(1 节点为热备/维修余量);备件以"整节点"计,不以"卡"计
- 电力/散热约束(量级):H100 SXM 700W/卡 → 单节点 ~6-7kW,单机架 8 节点需 50kW+ 供电 → **液冷成为大集群默认**(采购谈判时"节点功率密度"是硬参数)

**MTTR 目标(生产参考)**:节点故障检测 < 1min(heartbeat + NCCL watchdog),调度重建 < 5min,模型加载 + 预热 5-15min(按模型规模)→ **单节点故障的容量损失窗口 ~10-20min**,SLO 设计必须含这个窗口(Ch29 案例 9)。

## 19.3 集群级负载均衡

**全局请求路由(多副本之上的网关层)**:

1. **前缀感知一致哈希**:对 prompt 的前缀(首 N token 哈希)做 hash ring → 相同前缀落同一副本 → **prefix cache 命中率最大化**(Ch5:命中 = 跳过 prefill,TTFT 直降一个数量级);环上加虚拟节点做负载均衡
2. **副本级负载**:在哈希基础上叠加"副本队列深度/预估剩余 KV 余量"的偏移(软亲和:前缀命中且副本不过载才走,否则换最近副本)
3. **MoE 热 expert 路由**(Ch16 §16.3):副本上报 expert 占用向量 → 路由把请求导向"有富余热 expert 容量"的副本——把 expert 均衡抬到请求级
4. **SLO 分级**:高优先级池(独享副本)与普通池(共享副本)分路由(Ch29 案例 6 的多租户隔离)

**autoscaling(队列信号驱动,KEDA 类)**:

- **信号**:waiting 队列深度(主)、TTFT p95 vs SLO(主)、GPU util(辅,Ch10 踩坑框:util 不区分 roof)
- **粒度**:以 gang 副本为单位扩缩(整节点);**扩容前置时间 = 节点调度 + 模型加载 + 预热**(70B 级 ~分钟,671B MoE 级 ~10min+)→ **反应式扩容永远追峰值**,生产用"流量预测(历史曲线)+ 提前扩容"
- **缩容滞后(hysteresis)**:避免锯齿——缩容条件比扩容条件严格(如队列 < 阈值持续 10min 才缩)

## 19.4 成本与效率

**$/百万 token 模型(必须会手算)**:

```
$/M tokens = (卡数 × $/card-hour) ÷ (实测 goodput tok/时 ÷ 10⁶)
          = 卡数 × $/card-hour × 278 ÷ goodput(tok/s)    # 278 = 10⁶/3600
```

手算(示例,估算):70B TP8 单副本,H100 $2/card-hour(估算),实测吞吐 4000 tokens/s(Ch2 压测,含 60% 利用率修正)→
= (8 × 2) / (4000 × 3600 / 1e6) = 16 / 14.4 ≈ **$1.1 / 百万 token**。
两个修正项常被漏:① **利用率**(名义峰值吞吐 → 实测,通常打 5-8 折:调度间隙、混合负载、抢占);② **峰谷**(夜间低负载的空闲卡也是成本 → 混部或缩容)。

**SM 活跃率(效率看板主指标)**:DCGM `SM Active` 的时间加权平均——decode 服务典型 40-70%(低),prefill 重负载 80%+;与 $/M token 做回归,识别"花了钱没算力"的时段(Ch20 的 L3 层)。

**混部与抢占(推理/训练共用集群)**:

- 优先级:推理 SLO 副本 > 短任务推理 > 训练 gang;训练任务可被**整体抢占**(gang 归还,Ch14 §14.4)
- 被抢占的推理请求 = Ch6 的 preemption(recompute/swap 二选一)——**混部集群必须把抢占代价计入 SLO 预算**
- 隔离手段:小模型/多租户用 **MIG**(Multi-Instance GPU,硬件分区;H100 可切 7 实例,硬件级带宽/容量隔离)——注意 MIG 切分后 NVLink 受限,**MIG 实例内不做 TP**
- 成本口径:混部后"有效 $/card-hour"下降(空闲时段被训练利用)→ 财务口径 $/M token 用**加权利用率**重算

> **踩坑框:"我们 GPU util 90%,成本已经很低了"**
> 三个反问:① util 在哪个 roof 上(Ch10 踩坑框)?② $/M token 的利用率修正是按**峰值名义**还是**实测吞吐**算的?③ 峰谷时段谁在烧钱?util 高但 $/M token 不降 = 算力花在低算术强度的活上(小 batch decode 未合批),回 Ch1/Ch6 查调度。
