## 1.1 一次 forward:同一个模型,两种工作负载

以典型 decoder-only LLM 为例(取 Llama-3 70B 的规格):输入是长度 N 的 token 序列,hidden 维度 d=8192,L=80 层。每一层是两个 block:

```
x = x + Attention(RMSNorm(x))     # attention:QKV 投影 + QKᵀ/AV + 输出投影
x = x + MLP(RMSNorm(x))           # 前馈:SwiGLU,三组 GEMM
```

两个 block 的计算都由 **GEMM(矩阵乘矩阵)** 主导。一次 forward 的总 FLOPs 可以按量级估计:

> **FLOPs ≈ 2 × P × N**(P = 参数量,N = 本次 forward 的 token 数)

注意这个近似只数了 GEMM 部分,没数 attention 里 QKᵀ 与 AV 的 O(L·N²·d) 项——短上下文下它可忽略,长上下文下它会成为主角(第 11、17 章展开)。

现在到了本章的关键观察:**同一个权重矩阵 W ∈ R^{d×d′},在两种场景下的"用法形状"完全不同**:

| | Prefill(一次处理 N 个 prompt token) | Decode(每步生成 1 个新 token) |
|---|---|---|
| 输入形状 | X ∈ R^{N×d},N 可达 10³~10⁵ | x ∈ R^d,一个向量 |
| GEMM 本质 | 矩阵 × 矩阵 | 矩阵 × 向量(GEMV) |
| W 从 HBM 读出 | **1 次**,摊到 N 个 token 上 | **每一步都要全量读一遍** |
| 算术强度(AI) | O(N),数百到数千 | ≈ 1 FLOP/byte |

算术强度(arithmetic intensity,单位 FLOP/byte,即每从 HBM 读 1 字节做的浮点运算数)是 Roofline 模型的核心概念,1.5 节定量展开。先用手算感受一下:

**例 1-1  7B 模型,H100 SXM(HBM3 80GB,带宽 ≈ 3.35TB/s,FP16 稠密 ≈ 989 TFLOPS)**

- **Decode,batch=1**:权重 ≈ 7B × 2B = 14GB,每步都要完整读一遍。单步时间下界 ≈ 14GB ÷ 3.35TB/s ≈ **4.2ms**,即理论上限 ~230 tokens/s。实测经验 [估算] 7B 在 H100 上 batch=1 的 TPOT 通常 ~6-10ms——多出来的部分是 attention 的 KV 读取、激活、采样等开销——但结论不变:**下界由 HBM 带宽决定,与算力无关**。
- **Prefill 2048 tokens**:FLOPs ≈ 2 × 7×10⁹ × 2048 ≈ 2.9×10¹³,按 H100 峰值 ≈ **30ms**。2048 个 token 用 30ms,折合 ~100,000 tokens/s。
- 对比:prefill 的每 token 成本约为 decode 的 **~1/285(≈1/300)**(30ms/2048 token vs 4.2ms/token,同批 batch=1 口径)。同一个模型,一个"算力受限",一个"带宽受限"。

> **踩坑框:把上表读成"prefill 又快又便宜"**
> 新手常从上表得出"prefill 不重要"。错:prefill 受算力限制,长上下文(10⁴~10⁵ token)会把 TTFT 推到秒级甚至分钟级——Chunked Prefill(第 6 章)、Context Parallelism(第 17 章)、P/D 分离(第 9 章)全是为它服务的。"每 token 便宜"只在 batch=1 且上下文不长时成立。

这张"两种形态"的图是后面几乎全部优化的根:**面向 prefill 的手段(FA3、FP8、分块、CP)与面向 decode 的手段(batching、量化、KV 压缩、投机解码)作用于两个不同的物理瓶颈,用错场景基本无效**。

## 1.2 KV Cache 为什么是必然:用显存换计算

生成是自回归的:第 t 步生成 token t+1 时,必须 condition 于前面全部 t 个 token。attention 需要历史每个 token 的 K 和 V——**不缓存,就只能重算**。

算一下"不缓存"的代价:第 i 步要对 i 个历史 token 重算 K/V 并做 attention,N 步总计算是 Σ O(i) 的平方量级,总复杂度到 **O(N³·d)** 量级。KV Cache 把它变成:prefill 阶段一次性算好全部 K/V 写入 HBM,之后每步 decode 只做"新 token 的 q × 历史 K/V",O(N·L·d);总计算降为 O(N²·L·d)——**少了 N 的一个量级,N² 项消失**。对在线推理这不是优化,是必需品。

代价是显存。每层、每个 token 存一份 K 和一份 V:

> **(1-1)  KV / token = 2 × L × h_kv × d_head × bytes**
>
> 2 = K 和 V 两份;h_kv = KV head 数;d_head = 每 head 维度;bytes = FP16/BF16 取 2,FP8 取 1

**例 1-2  Llama-3 70B(L=80,h_kv=8,d_head=128,BF16)**

KV/token = 2 × 80 × 8 × 128 × 2B = **320KB**

即每个请求:8K 上下文 ≈ 2.5GB,32K ≈ 10GB。128 个并发 32K 请求 ≈ 1.3TB KV——直接超过任何单机。第 3 章会用这个公式反推"要买多少卡",第 5 章讲怎么分页管理,第 8 章讲怎么减半(FP8 KV)。

注意一个关键区别:**KV 不能"免费重算"**。历史每个 token 的 K/V 都要被新 token attend 到,重算是真实计算(唯一的例外是第 6 章的抢占 recompute 策略,而它的代价正是我们刚算的 O(N²) 重放)。这是 KV 与训练侧 activation checkpointing 的本质区别:后者重算的是"中间激活",且可以整段重放;前者重算的是"对每个历史 token 的全部线性层",在线场景下几乎不可承受。

## 1.3 GQA / MQA:模型侧的第一道 KV 优化

KV 体积正比于 h_kv,而最小化 h_kv 的第一手段在**模型训练侧**:

- **MHA**(标准 multi-head attention):每个 q head 一份 K/V,h_kv = h_q
- **GQA**(grouped-query):一组 q head 共享一份 K/V。Llama-3 70B:h_q=64、h_kv=8 → **KV 体积是 MHA 的 1/8**
- **MQA**:所有 q head 共享一份 K/V,h_kv=1,KV 最小,但质量损失相对更大

两点强调:

1. GQA/MQA 是**模型侧的决策**,serving 框架无法事后给一个 MHA 模型"省 KV"。框架能做的只有 (1-1) 之后的后处理:量化、选择性保留、offload(第 5、8 章)。这也是"模型架构"会出现在部署书里的原因——**它决定了优化空间的地板**。
2. decode 阶段读 KV 是 HBM 流量的大头。batch 小、上下文长时,KV 流量可以与权重流量相当甚至超过。所以 GQA 除了省显存,还**直接加速 decode**——这是 70B 级模型几乎全用上 GQA 的原因,也是例 1-2 里 h_kv=8 而不是 64 的原因。

## 1.4 为什么推理"难":三重矛盾,与"堆卡"的边界

把 1.1-1.3 放在一起,推理系统的困难可以浓缩成**三重矛盾**:

| 矛盾 | 内容 | 典型症状 |
|---|---|---|
| 显存 × 并发 | KV 随 batch × 上下文线性增长,上限由显存决定 | 拒绝请求、OOM、上下文被截断 |
| 算力 × 延迟 | 长 prefill 是算力活,短 decode 是带宽活,两者资源画像冲突 | TTFT 高、TPOT 尖刺 |
| 吞吐 × 尾延迟 | 提高 batch 吞吐涨,但抢占、长 prefill、通信抖动制造长尾 | p99 远差于 p50 |

**为什么"堆卡"不能通用地解决**(面试常追问,至少给三条):

1. **TP 有通信上限**:每层 2 次 all-reduce,规模一大,通信延迟 × 层数吃掉收益,TP 基本被锁在节点内 NVLink 域内(第 14、15 章定量)。
2. **KV 不能简单"分卡放"**:一个请求的 attention 需要它完整的 KV;真正切序列的是 CP,而 CP 引入自己的通信(第 17 章)。MoE 的专家通信又是另一种模式(第 16 章)。
3. **堆卡不解决长尾与稳定性**:p99 尖刺来自抢占、热 expert、通信 straggler 等调度/系统事件,加副本只抬容量,不降尾(第 21、22 章)。

所以,推理优化真正做的是:**在固定资源上把三个杠杆拧到极限**——

- **显存杠杆**:管好 KV(PagedAttention、前缀缓存、量化、offload)→ 第 3、5、8 章
- **计算杠杆**:把每 FLOP 变快(FlashAttention、FP8/FP4、kernel 融合、MoE 算子)→ 第 8、11、12、13 章
- **调度杠杆**:决定"算什么、按什么顺序、怎么组 batch"(continuous batching、chunked prefill、抢占、投机解码、P/D 分离)→ 第 6、7、9 章

(还有第四个维度——**分布式**:TP/EP/PP/CP 决定上面三个杠杆如何在多卡多机上摆放,见 Part IV。)

## 1.5 [进阶] 定量视角:Roofline 模型

把"算力受限 / 带宽受限"说精确,需要两个量:

- **算术强度** AI = FLOPs / 读取的字节数(FLOP/byte)
- **机器的 ridge point** = 峰值 FLOPS ÷ 峰值 HBM 带宽

H100(FP16):989 TFLOPS ÷ 3.35 TB/s ≈ **295 FLOP/byte**。含义:

- **AI < 295**(memory-bound):实际 FLOPS ≈ AI × 带宽。提升手段是**抬高 AI**(加大 batch、量化减小权重体积)或减少字节数(压缩 KV)。
- **AI > 295**(compute-bound):性能 ≈ 峰值 FLOPS × MFU。提升手段是更高效的 kernel(FA3)、更低精度算力(FP8 翻倍)。

套用到 1.1 的两种形态:

- **Decode(GEMV)**:每读 2 字节权重做 2 次浮点 → **AI ≈ 1**,深度 memory-bound。这就是"batching、量化、KV 压缩对 decode 有效"的数学根据。
- **Prefill(N 个 token 共享一次权重读取)**:FLOPs ≈ 2PN,权重读 ≈ 2P(BF16)→ **AI ≈ N**。N=1024 时 AI≈1000 » 295 → compute-bound。
- **交叉点**:N ≈ 295 → **N ≈ 300**。即"batch × 上下文"要到数百量级,GPU 才从带宽受限翻到算力受限。

> **这是 continuous batching 的定量根据**(第 6 章的开场):提高 batch 不是"多排队",而是把 decode 的 AI 从 1 抬到上百,理论上把 decode 吞吐抬高近两个量级(直到被 KV 显存和调度事件限制)。

> **精度声明**:以上是量级估计,未计 KV 读取、attention 的 N² 项与 MFU(<100%)。目的是建立"量级感",不能当部署参数用——部署级数字一律实测(第 2 章)。

## 1.6 小结:三大杠杆与全书地图

| 杠杆 | 物理瓶颈 | 代表技术 | 章节 |
|---|---|---|---|
| 显存 | HBM 容量 | PagedAttention、前缀缓存、FP8 KV、offload | 3、5、8、21 |
| 计算 | FLOPS / 带宽 | FA3、FP8/FP4、kernel 融合、MoE 算子 | 10-13 |
| 调度 | 时间片分配 | Continuous Batching、Chunked Prefill、投机解码、P/D 分离 | 6、7、9 |
| 分布式 | 通信 | TP/EP/PP/CP、NCCL、拓扑 | 14-19 |
| 闭环 | 从指标到落地 | 性能分析、OOM、长尾、生产部署 | 20-23、25-27 |

记住本章的一句话:**prefill 是算力的活,decode 是带宽的活,调度是时间的活,分布式是通信的活;混着做,基本无效。**
