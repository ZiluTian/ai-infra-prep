## 23.1 serving 栈

```
客户端
 └─ LLM 网关(自研或开源:Envoy 类 / 专用 LLM 网关)
     ├─ 路由: 前缀感知哈希 + 副本负载 + SLO 预算(Ch19 §19.3)
     ├─ 限流: 租户级 QPS/token 预算(过载 shed 的第一层,Ch22 §22.3)
     ├─ 灰度: 版本影子/切流(§23.4)
     └─ 重试/去重: 崩溃恢复语义(Ch21 §21.4)
 └─ 副本(引擎:vLLM/SGLang/TRT-LLM)
     ├─ 调度器(Ch6): continuous batching + chunked prefill + 抢占
     ├─ KV 管理(Ch5): paged pool + prefix cache(RadixCache)
     └─ 算子/并行(Ch10-18)
 └─ 基础设施: K8s + gang 调度(Ch14)、监控(DCGM/Prometheus)、网络(Ch18)
```

**层职责边界(面试讲架构的骨架)**:

- **网关层**知道:租户、SLO 等级、前缀、副本状态;**不知道** token 级调度
- **引擎层**知道:batch 构成、KV block、step 时间;**不决定**请求进哪个副本
- **反模式**:让引擎做全局路由(它看不到全副本状态)/ 让网关做 token 预算(它看不到 KV 余量)——**信息在哪层,决策就在哪层**

**负载均衡策略对比**:

| 策略 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| least-queued(队列最短) | 简单、抗不均 | 忽略前缀亲和 → cache 命中率低 | 无前缀复用的负载 |
| **前缀感知 + 软亲和**(Ch19) | cache 命中 ↑(TTFT ↓ 一个量级)+ 负载均衡 | 实现复杂(哈希环 + 状态上报) | 通用(默认选它) |
| 预测耗时感知(SLO 预算) | p99 最优(Ch22) | 需要耗时预测模型 | 双 SLO 严格场景 |

**副本管理**:版本标签(模型 + 引擎版本 + 配置指纹三件套,任一变化 = 新版本)、drain(Ch21 §21.4)、健康检查(三层:进程活 → 能算 → **延迟正常**(慢副本要摘流量,不是摘活))。

## 23.2 监控与告警(指标清单)

**请求级(SLO 直接挂钩,必报 p50/p95/p99)**:

```
TTFT p50/p95/p99(分输入长度桶: ≤4K / 4-32K / >32K —— 不分桶的 TTFT 没有信息量)
TPOT p50/p95/p99(即 ITL 均值,Ch2)
端到端时长 p99、成功率、拒绝率(429 占比 = 过载信号)
```

**系统级(引擎自报)**:队列深度、running batch、KV pool 使用率、prefix cache 命中率、抢占计数、spec decode 接受率(若开,Ch7)

**硬件级(DCGM/NCCL)**:GPU util(辅助,Ch10 踩坑框)、**SM Active + SM clock + throttle 原因**、功耗、NVLink 错误计数、IB 吞吐/错误、ECC/XID

**告警设计(SLO 导向,不是固定阈值)**:

1. **SLO 燃烧率告警**(Ch22 §22.4):p95 TTFT 预算、p99 TPOT 预算各一套双窗口
2. **容量告警**:KV 使用率 > 80% 持续 5min(P2);抢占计数 > 0 持续 1min(P2,Ch21)
3. **硬件告警**:NVLink 错误计数增长(P1,Ch20 案例 B)、throttle 原因非空持续(P2)
4. **反模式:只报 GPU util**——util 100% 可能是 memory-bound 低效(Ch10),util 低可能是 CPU 瓶颈(Ch20 §20.2)。**告警报"业务坏没坏 + 资源在不在 roof 上",不报"忙不忙"**

## 23.3 [进阶] 容量规划(Ch3 的生产版)

**从流量到卡数(完整链条,必须能白板推)**:

```
① 流量预测: req/s 曲线(日峰/谷 + 季节 + 增长,季度口径 Ch29 案例 10)
② 负载画像: 输入/输出长度分布(分位)→ 每请求 prefill/decode 计算量
③ 单副本能力(实测,Ch2 压测):
   - prefill 容量: tokens/s(prefill 池)
   - decode 容量: 并发数 × (1/TPOT 目标),受 KV pool 上限钳制(Ch3 公式)
④ 卡数 = ceil(峰值流量 / 单副本能力) × 副本数 × (1 + 余量)
   余量: 故障域(N/(N-1),Ch19 §19.2)+ 突发(20-40%)+ 灰度(1 个旧版本副本)
⑤ 成本: 卡数 × $/card-hour × 利用率(Ch19 §19.4)
```

**关键细节(面试区分点)**:

- **峰谷策略**:按峰值配 = 夜间 50% 卡烧钱;解法 = 缩容(冷启动成本,Ch19 §19.3)+ 混部(§19.4)
- **P/D 配比**:prefill 池 : decode 池 = (输入 token/s 需求) : (输出 token/s 需求),由负载的**输入/输出长度比**决定(Ch9 §9.5)
- **余量不是拍脑袋**:故障域余量 = 1 个 gang 组(硬约束);突发余量 = 压测"3× 突发 30min"下 SLO 是否守住(Ch22 shed 是兜底不是常态)
- **成本归因**:按租户计费 → 每租户的 token 数 × 该租户的 SLO 等级(高优池成本 > 普通池,Ch19)

## 23.4 [进阶] 发布与回归

**性能回归 CI(nightly,固定负载 + 固定硬件)**:

```
nightly: 固定 benchmark 集(3 种负载: 短对话 / 长文档 / 高并发混合)
         → 指标: 吞吐、TTFT/TPOT p95、KV 命中率
         → 门禁: 任一指标退化 > 5% 阻断发布(基线 = 上一版本,不是绝对值)
硬件: 固定节点(排除硬件变量);模型权重固定 commit
```

**灰度与回滚(发布流程)**:

1. **5% 流量 + SLO 门禁**:新版本副本接 5% 流量,观察 30min-2h(覆盖一个业务小峰)
2. **门禁指标(自动)**:SLO 燃烧率、错误率、p99、**吞吐/卡**(性能回归的在线版)
3. **自动回滚**:门禁任一触发 → 流量切回旧版本(网关层切流,秒级);引擎层保留双版本(Ch23.1 的版本三件套)
4. **kernel/框架升级特殊流程:A/B + shadow**
   - A/B:新旧 kernel 各跑 50% 副本,对比在线指标(统计显著性:样本量 = 请求数 × 时长,别只看 10 分钟)
   - shadow:新版本**跑但不返回**(影子流量,结果丢弃)→ 零风险验证稳定性,只验证性能

> **踩坑框:"线上灰度没问题,全量就炸"**
> 三个经典原因:① 5% 流量没覆盖**长尾负载**(超长上下文/极端 batch 组合只在 5% 之外)→ 灰度流量按**负载类型加权抽样**,不只按请求数;② 灰度副本与全量副本**硬件不同**(老节点/新节点混部)→ 固定灰度节点;③ 回滚不彻底(配置/权重版本与引擎版本错位)→ 版本三件套指纹校验。
