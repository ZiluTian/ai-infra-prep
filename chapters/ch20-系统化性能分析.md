## 20.1 三层分析框架

```
L1 宏观(分钟级,看指标时序): TTFT / TPOT / 吞吐 / GPU util / 队列深度,各取 p50 + p99
   → 回答:"什么变坏了?什么时候开始?影响面多大?"
L2 组件(小时级,看分段): 把时间拆到 排队 / prefill / decode / 通信 / 采样 / 调度
   → 回答:"哪个组件贡献了异常?"
L3 kernel(天级,抓 profile): nsys timeline + ncu(SOL / occupancy)+ DCGM(时钟/功耗)
   → 回答:"这个组件内部,时间花在哪个 kernel / 哪种等待?"
```

**方法论(面试必背)**:**先 L1 定"什么坏了",再 L2 定"哪个组件",最后 L3 定"为什么"**。上来就 nsys 抓 kernel 的三个问题:① 抓的位置可能根本不在异常路径上;② profile 本身有开销(扰动系统);③ kernel 级证据无法回答"是不是排队问题"这类系统级假设。**L1/L2 的证据(指标时序)几乎零成本,L3 成本高——成本顺序就是分析顺序**。

**L2 分段怎么拿到**:

- TTFT = 排队时间 + prefill 时间(网关入口时间戳 → 首 token 时间戳;vLLM/SGLang 的 per-request trace 直接给两段)
- TPOT = decode 步时 / batch + 步间 gap(调度器日志:每步 batch 构成、每步耗时)
- 通信段:NCCL 时间戳 / nsys 里 all-reduce kernel 区间
- 关键技巧:**异常请求与正常请求的分段对比**(同模型同负载下,p99 请求 vs p50 请求的组件时间差 = 异常来源)

## 20.2 症状 → 原因库(案例驱动)

| 症状 | 候选原因(按先验概率排序) | 第一证据 |
|---|---|---|
| **TTFT 高** | ① 排队(并发超容量)② 长 prefill(上下文长)③ chunked prefill 没开/太小 ④ 前缀冷(cache 命中率低)⑤ 路由把长请求送给了满载副本 | 队列深度时序 + TTFT 与输入长度相关性 |
| **TPOT 高** | ① decode batch 太小(AI 低,Ch1)② launch 开销(graph 没开,Ch12)③ TP 过大跨机通信(Ch15)④ 通信 straggler / 热 expert(Ch16)⑤ 降频(clock throttle,DCGM)⑥ 抢占重算(Ch21) | decode 步时直方图 + nsys gap 占比 + DCGM 时钟 |
| **吞吐低但延迟正常** | ① 显存碎片(KV pool 用不满,Ch5)② 抢占风暴(反复 recompute,Ch21)③ 负载结构(短请求多、合批差)④ 路由不均(副本间负载差 2×) | KV 使用率 vs 名义容量 + 抢占计数 + 副本间请求数 |
| **GPU util 低** | ① CPU 瓶颈(tokenize / 调度 / 采样在 CPU,Ch6/Ch12)② 通信等待(RDMA 慢,Ch18)③ CUDA graph 没生效(动态 shape 逃逸出图)④ 负载本身就低(不是故障)⑤ 降频 | nsys gap 类型 + graph 捕获日志 + DCGM throttle |
| **p99 尖刺(点状)** | ① 通信事件(单卡 NVLink 降级 / PFC 风暴)② 抢占发生 ③ 长 prefill 进入 ④ GC/调度停顿 ⑤ MoE 热 expert 步 | 尖刺时刻与系统事件(日志)对齐 |
| **p99 慢性高(面状)** | ① 容量不够(系统性排队)② 负载结构不匹配(长上下文占比高)③ 架构错配(该 P/D 没 P/D) | p99/p50 比值时序 + 负载构成统计 |

**用法**:症状进库 → 按先验概率逐个排除(每个假设一条便宜的证据)→ 命中后进 L3 深挖。

## 20.3 工具链实操

**vLLM / SGLang 内置指标(第一现场,零成本)**:

- `num_requests_waiting`(排队)、`num_requests_running`(decode batch)
- `gpu_cache_usage`(KV pool 使用率,碎片问题的主指标)
- prefix cache 命中率(命中 = 省 prefill,Ch5)
- 抢占计数(`num_preempted`):> 0 持续出现 = 容量信号
- 每请求 trace(`log_stats`):TTFT/ITL 分段

**nsys(gap 分析,Ch10 §10.4 的深化)**:

- **CPU gap vs kernel gap**:GPU 空闲且 CPU 有 python 活动 → CPU 瓶颈;GPU 空闲且 CPU 也空 → 通信等待/同步阻塞
- **CUDA graph 生效验证**:decode step 的 kernel 发射应呈"图内密集 + 图外稀疏";若每个 kernel 都是独立发射间隔 → graph 没生效(动态 shape 逃逸)
- 抓法:稳态负载下抓 30-60s,别抓冷启动

**ncu(单 kernel SOL)**:GEMM 的 Memory % vs Compute %(Ch10);**decode 的 GEMV 期望 Memory SOL 70-90%**(贴带宽 roof),低于 60% 查 occupancy/量化/dequant 开销。

**DCGM(硬件状态)**:`dcgmi dmon` 的 SM clock、功耗、**throttle 原因**(HW Slowdown = 温度/电压,SW Power Cap = 功耗墙)→ 降频是"TPOT 高"的第五号嫌疑,必须排除。

## 20.4 三个完整案例(症状 → 假设 → 证据 → 修复 → 回归)

### 案例 A:GPU util 35%,TPOT 达标,吞吐上不去

- **L1**:峰值时段 util 35%(SM Active 40%),TPOT p95 达标,吞吐只有压测基线的 60%
- **L2**:分段看 decode——单步 kernel 时间正常(5ms 级),但 `num_requests_running` 均值仅 5-8;`gpu_cache_usage` 只有 40%(KV 余量充足)
- **假设**:decode batch 太小 → AI 低(Ch1:AI≈batch),单步虽快但合批差 → 吞吐 = batch × 1/step_time 上不去
- **证据**:nsys timeline:decode 段 gap 占 50%(CPU 在等,不是 GPU 慢);ncu GEMV Memory SOL 65%(batch 小,未贴 roof)
- **根因**:`max_num_seqs=8` 配得太保守(当初为延迟设的),且 chunked prefill token 预算小 → 新请求进不来
- **修复**:`max_num_seqs` 8 → 64,chunk 预算 2K → 8K,同时盯 TPOT p99(容量换来的延迟代价)
- **回归**:吞吐 60% → 92% 基线;TPOT p95 +8%,p99 +20%(记录在案,与业务确认可接受);util 35% → 68%

### 案例 B:TP8 的 TPOT p99 偶发尖刺(p99 = 3×p50)

- **L1**:p50 正常(8ms),p99 偶发 20-30ms,点状分布,无时段规律
- **L2**:对尖刺请求做分段——decode 步时正常,**all-reduce 段偶发 30×**(NCCL 时间戳/nsys)
- **假设**:通信通道问题(候选:NVLink 链路降级 / NIC 争用 / PFC)
- **证据**:① `nvidia-smi topo -m` 发现某两卡 `NV18 → NV8`(链路降速,硬件);② DCGM NVLink 错误计数增长;③ NCCL_DEBUG=INFO 显示 channel 数减半
- **根因**:一根 NVLink 线缆问题(节点搬动后),链路自动降速
- **修复**:换线,恢复 18 links;同时加**NVLink 错误计数的告警**(DCGM exporter)
- **回归**:p99/p50 从 3× 回到 1.6×;经验:**点状 p99 尖刺先查硬件链路,再查软件**

### 案例 C:长 prompt 到来时,decode 请求集体卡顿

- **L1**:某时段(批量长文档导入)TTFT 与 TPOT 同时恶化:TTFT 10s,在跑请求 TPOT 8ms → 60ms
- **L2**:分段——一条 128K prefill 占 200ms 级步时间,连续多步;decode 请求被插队等待
- **假设**:prefill 未分块(chunked prefill 未开 / chunk 过大)
- **证据**:配置检查:`chunked_prefill` 未启用;nsys 里 prefill 步与 decode 步交替,decode 步前有大 gap
- **修复(两级)**:
  1. 短期:开 chunked prefill(chunk 8K)→ decode 步时恢复 8-11ms,长 prefill 被切块摊平
  2. 长期:该负载满足 Ch9 判据(长上下文 + 高负载 + TTFT/TPOT 双 SLO)→ 立项 **P/D 分离**(prefill 池独立扩缩,decode 池纯净)
- **回归**:chunked prefill 后 TTFT p95 10s → 4s(排队减少),TPOT p99 60ms → 11ms;P/D 上线后 TTFT 再降 40%(prefill 池加卡),decode 池零长 prefill 干扰
- **经验**:chunked prefill 是"步级"答案,P/D 是"结构级"答案——**先用便宜的一级,满足不了判据再上结构级**
