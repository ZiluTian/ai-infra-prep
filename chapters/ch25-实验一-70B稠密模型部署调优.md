## 25.1 基线(vLLM TP8 默认参数)

```bash
vllm serve Qwen/Qwen2.5-70B-Instruct --tensor-parallel-size 8 \
  --port 8000 &                          # 全部默认:gpu_mem_util 0.9, block 16, chunked prefill 默认开(v1,Ch6 §6.3)
python labs/bench_load.py --base-url http://localhost:8000/v1 --model Qwen2.5-70B-Instruct --profile mixed --duration 300
```

**期望结果**:权重 140GB FP16(TP8 每卡 17.5GB)+ KV 池 ~52GB/卡(Ch3 例 3-1 同款口径:72−17.5−2);短对话 TPOT ~10-15ms、TTFT p95 < 1s(batch 64);记录**全部**指标进记录表 #1。

**常见失败模式**:启动 OOM(70B FP16 权重 140GB + KV:4×A100-40G 共 160GB 装不下 → 换 `--quantization fp8` 或 80G 卡);NCCL 初始化慢(正常,首次 ~1-3min);首请求慢(冷启动预热,压测前 warm-up 10 条)。

**思考题**:基线的 decode 处于哪个 roof(用 Ch10 公式算 AI)?哪个指标最可能先触顶(KV 池 vs 算力)?

## 25.2 参数调优矩阵(4 旋钮,单变量)

| 旋钮 | 扫描 | 看什么指标 |
|---|---|---|
| `max_num_seqs` | 128 / 256 / 512 | 吞吐 ↑ 至何时 TPOT p99 恶化;KV 使用率 |
| `gpu_memory_utilization` | 0.85 / 0.90 / 0.95 | KV 池大小 → 并发上限;0.95 时激活 OOM 风险(Ch21) |
| `max_num_batched_tokens` | 2048 / 8192 / 32768 | 长短混合下 TPOT p99(chunk 效应,Ch6) |
| `block_size`(kv) | 16 / 32 / 64 | 碎片率、KV 命中率(Ch5 §5.2);一般差异 <2%,**验证"默认值通常不是瓶颈"** |

每组 120s 压测(同负载),记录表 #2-#5。**期望结果**:max_num_seqs 与 batch 预算是**主收益项**(吞吐 +20-50% 常见);block_size 差异微小。**思考题**:为什么 block_size 64 的"理论碎片减半"没体现?(答案方向:碎片在 paged 体系里已被 block 化吸收,见 Ch5 §5.2)

## 25.3 Prefix Caching(50% 复用负载)

```bash
# 开:--enable-prefix-caching
# 负载:50% 请求共享 4K 系统前缀(§25.0),其余 50% 随机前缀
python labs/bench_load.py --base-url http://localhost:8000/v1 --model Qwen2.5-70B-Instruct --profile prefix50 --duration 300
```

**期望结果**:TTFT p95 降 **40-70%**(复用部分跳过 prefill,Ch5 §5.4);vLLM metrics 前缀命中率 = `vllm:prefix_cache_hits / (vllm:prefix_cache_hits + vllm:prefix_cache_misses)` ≈ 50% 附近;吞吐同比例升。
**常见失败模式**:命中率远低预期——检查请求前缀是否**逐字节相同**(温度参数/时间戳进了 prompt 就全 miss);流式客户端把每轮对话全量重发(命中的是整段,设计问题不是引擎问题)。
**思考题**:命中率 50% 时,decode 侧吞吐为什么也会涨?(提示:prefill 算力释放 → 排队减少 → 调度更顺,Ch20 L2 分段验证)

## 25.4 Chunked Prefill(长短混合)

```bash
# v1 下 chunked prefill 默认开;本节"对照"= 关它(`--no-enable-chunked-prefill`)与默认开对比
# 扫描 --max-num-batched-tokens 2048/8192/32768
# 负载:§25.0 混合(80% 短 + 20% 8K 长)
```

**期望结果**:开 chunked 前,长请求进入时**所有在跑请求 TPOT 尖刺**(Ch20 案例 C 复现);开 chunked 后 TPOT p99 回落 ~50-80%,代价:短请求 TTFT 略升(与长请求共享步)。
**常见失败模式**:chunk 太大(32K)→ 尖刺仍在;太小(2K)→ 长请求 TTFT 恶化 + 调度碎片。**思考题**:你的负载输入/输出比 8:1 还是 1:8,分别选多大 chunk?(方向:输入重 → 大 chunk 摊 prefill;输出重 → 小 chunk 保 decode 步时)

## 25.5 Speculative Decoding(batch 扫描)

```bash
# 方案 A(n-gram,免训练):--speculative-config '{"method":"ngram","num_speculative_tokens":5}'
# 方案 B(有 EAGLE 权重):method=eagle
# batch 扫描:1 / 8 / 32 / 128,各 120s
```

**期望结果(验证 Ch7 §7.4 预测)**:batch 1 → 1.5-3×(负载自重复高时 n-gram α 高);batch 32 → ~1.1-1.5×;batch 128 → ~1.0×(甚至 <1)。**画"加速比 vs batch"曲线**——这张图就是 Ch28-B 题"投机解码什么时候失效"的实证。
**常见失败模式**:α 异常低(<0.3)→ 检查负载类型(高熵任务 n-gram 无效,换 EAGLE);接受长度恒为 0 → draft 配置与模型不匹配(词表/家族)。
**思考题**:n-gram 在"代码补全"负载上 α 为什么可能 > 小模型 draft?

## 25.6 瓶颈分析(nsys 拆解)

```bash
# 稳态负载下:nsys profile --trace=cuda,nvtx -o /tmp/exp1 --duration 120
# 拆解:一个 decode 步与一个 prefill 步的 kernel 组成
#   decode 步: GEMV/GEMM 时间、attention、通信(all-reduce)、gap、launch 段
#   prefill 步: GEMM 占比、FA 占比、通信占比
```

**期望结果(量级)**:decode 步 GEMM ~60-70% + attention ~15% + all-reduce ~10-15% + 其余;prefill 步 GEMM+FA ~85%+。ncu 抽 decode GEMV:Memory SOL 应 70-90%(Ch20 §20.3)。**若 all-reduce 占比 >25% → 回 Ch15/18 查拓扑与 NCCL**。
**思考题**:用 Ch10 roofline 把 decode GEMV 的 AI 画上图——你测的 SOL 离 roof 还有多少?剩余空间归因(量化?occupancy?)
