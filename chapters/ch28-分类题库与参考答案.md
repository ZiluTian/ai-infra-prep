## A 基础与指标(20 题)

**A1(★★★)prefill 与 decode 的本质差异?**
3min:prefill 一次算 N 个 token,compute-bound(AI≈N);decode 每步 1 token,GEMV 主导,memory-bound(AI≈1)。**两种形态 → 两套优化方向:prefill 榨算力(FA3/FP8/CP),decode 榨带宽(batch/量化/KV 压缩)。**
10min:手算两侧 AI(Ch1 例 1-1);TTFT 由 prefill 决定、TPOT 由 decode 决定;混合步(chunked prefill)的 AI 介于两者之间。
追问:为什么"prefill 快"不等于"用户体验好"?| Ch1/Ch2

**A2(★★★★)手算:70B GQA 模型,8K 上下文,每请求 KV 显存?TP8 每卡多少?**
3min:2 × layers × kv_heads × head_dim × bytes × seq(全模型)。70B:2×80×8×128×2B ≈ 320KB/token(全模型)→ TP8 后 40KB/token/卡 → 8K ≈ **0.32GB/卡(全模型 2.56GB/请求)**。
10min:GQA kv_heads=8(不是 64 个 q heads!);FP8 KV 减半;block 对齐误差 +5%;KV 池上限反推并发(Ch3 公式链 (3-1)~(3-5))。
追问:MLA 模型怎么改这个公式?| Ch3/Ch5/Ch17

**A3(★★★★)Roofline 是什么?H100 的 ridge point?decode GEMV 落在哪?**
3min:AI = FLOPs/bytes;roof = min(峰值, AI×带宽);H100 FP16 ridge ≈ 989/3.35 ≈ **295 FLOP/byte**;decode GEMV AI≈1 → 深度 memory-bound,可达性能 = AI×带宽(峰值的 ~3%)。
10min:MFU 3% 不是 bug 是物理;优化家族分 bound 讨论;用 labs/roofline.py 画。
追问:什么时候 decode 会翻成 compute-bound?| Ch10

**A4(★★★)TTFT / TPOT / ITL 定义与测量口径?**
3min:TTFT = 请求进入 → 首 token(含排队 + prefill);TPOT = (总时长 − TTFT) / (输出 token 数 − 1);ITL = 相邻 token 间隔(TPOT 是其均值口径)。**分位数必须报 p50/p95/p99,均值会骗人。**
10min:TTFT 分段(排队/prefill,Ch20 L2);ITL 尖刺的来源(抢占/长 prefill 入步/通信,Ch22);流式 vs 非流式测量的差异。
追问:为什么 p99 必须分输入长度桶报?| Ch2/Ch20/Ch22

**A5(★★★★)GQA 与 MHA/MQA 的关系?为什么 GQA 是主流?**
3min:MHA kv=q heads(64);MQA 1 个 kv head(质量掉);GQA 折中(如 8 个 kv head 服务 64 个 q head,分组共享)。**收益:KV 显存 ÷ 组数(8×),质量近 MHA。**
10min:TP 下 kv head 切分与复制(Ch15 §15.1);GQA 对 paged attention block 布局的影响;MLA 是 GQA 的极端化(压缩为 latent,Ch11 §11.5)。
追问:GQA 8 kv head + TP16 怎么办?| Ch3/Ch15

**A6(★★★★)"batching 三级跳"指什么?**
3min:① static batching(齐了才走,等待浪费)→ ② continuous batching(步级进出,Ch6)→ ③ chunked prefill(长 prefill 切块进同一步,消尖刺)。**每跳解决一个问题:等待、资源碎片、步时尖刺。**
10min:continuous batching 的调度器细节(waiting/running 队列、token 预算);chunked prefill 与 P/D 的边界(步级 vs 结构级,Ch9)。
追问:三级跳后还有什么"跳"?| Ch6/Ch9

**A7(★★★★)goodput 是什么?为什么比吞吐更适合生产?**
3min:goodput = 满足 SLO 的请求速率(Ch2 (2-5))。吞吐可以靠牺牲尾延迟堆出来(大 batch),goodput 把 SLO 约束进目标函数。**容量规划与扩容决策用 goodput,不用吞吐。**
10min:goodput 曲线的形状(随并发先升后降,拐点 = SLO 边界);与 SLO burn rate 的关系(Ch22 §22.4)。
追问:TTFT 和 TPOT 双 SLO 时 goodput 怎么定义?| Ch2/Ch22

**A8(★★★★)什么是"负载画像"?压测为什么要构造负载而不是随机文本?**
3min:负载画像 = 输入/输出长度分布 × 到达率 × 前缀复用率 × 内容分布。**生产负载高度非随机(系统提示词复用、长短混合、周期性),随机文本压测的结论不可外推。**
10min:构造方法(长短混合/前缀 50% 复用/偏斜 MoE 负载,Ch25-27 的 bench_load 脚本);压测报告的"可复现性"要求(命令 + 负载 + 硬件快照)。
追问:前缀复用率 50% 对 TTFT 的影响量级?| Ch2/Ch25

**A9(★★★★★)为什么 decode 是 memory-bound?怎么验证?**
3min:每步要读全量权重(70B = 140GB FP16)算 1 个 token → AI ≈ 2×70e9/1.4e11 ≈ 1 ≪ ridge 295。**验证三步:ncu 抓 GEMV kernel 看 Memory SOL(期望 70-90%)→ 加大 batch 看性能何时脱离线性 → 量化(FP8)看是否 ~2×。**
10min:batch 增大抬 AI 的曲线(Ch1);H200 带宽 +44% → decode +30-40% 的对照验证;KV attention 的 O(N) 读取在长上下文时的贡献(Ch11 FlashDecoding)。
追问:batch=128 时还是 memory-bound 吗?| Ch1/Ch10/Ch12

**A10(★★★★)KV 增长对 batch 上限的影响?怎么算"KV 池能装多少并发"?**
3min:并发上限 = KV 池字节 / (每 token 字节 × 平均上下文)。70B TP8 H100:KV 池 ~52GB/卡(Ch3 例 3-1),**40KB/token/卡**(320KB 全模型 ÷ 8)→ ~1.27M token 总量/卡;平均上下文 4K → **并发 ~310**。**KV 池是并发的第一约束(不是 max_num_seqs)。**
10min:长短混合时的实际并发(长请求挤占);FP8 KV / prefix cache 命中对上限的影响;`max_num_seqs` 与 KV 上限谁先触顶(Ch25 §25.2)。
追问:为什么 nvidia-smi 显存满了但 gpu_cache_usage 只有 0.6?| Ch3/Ch5/Ch21

**A11(★★★★)continuous batching 的调度循环长什么样?和 static batching 比,资源利用率为什么高?**
3min:每步(几 ms)重新组 batch:waiting 队列按 token 预算收请求、running 中完成的移出、新请求从 waiting 进来。static batching 要等最慢请求 → 短请求陪跑;continuous 步级进出 → **没有"等齐"浪费**。
10min:vLLM v1 调度器细节(waiting/running、token 预算 = max_num_batched_tokens);抢占(recompute/swap,Ch21);调度器是 CPU 单线程 → v1 双进程模型(Ch4)。
追问:调度循环每步的 CPU 开销量级?会不会成为瓶颈?| Ch4/Ch6/Ch20

**A12(★★★★)KV cache 为什么必须存?能不能像 RNN 只存 hidden state?**
3min:attention 需要历史所有 K/V 与当前 q 做内积;hidden state 是压缩的、有损的,无法重建精确 attention → **KV 是 attention 的"记忆",不压缩就必须在**。
10min:KV 显存 = 推理的第一容量约束(Ch3);压缩路线:GQA(结构)/量化(FP8,Ch5 §5.5.1)/MLA(latent)/sliding window;KV 传输成本(P/D 分离,Ch9)。
追问:sliding window 模型为什么 KV 显存 O(窗口)?| Ch3/Ch5/Ch11

**A13(★★★★)token 预算与序列上限(max_num_batched_tokens / max_num_seqs)各管什么?**
3min:token 预算 = **每步**最多处理的 token 数(prefill+decode 合计)→ 管步时长;序列上限 = 同时跑的请求数 → 管 KV 占用。**两个旋钮正交:预算大 = 长 prefill 能进(但步变尖),序列大 = 并发高(但 KV 吃紧)。**
10min:长短混合负载下两者的交互(Ch25 §25.2 扫描表);与 chunked prefill 的关系(预算就是 chunk 的总闸)。
追问:预算 8K 时,一条 8K 长请求进入对 decode 步的影响?| Ch6/Ch25

**A14(★★★★)首 token 延迟(TTFT)由哪几段构成?各段怎么优化?**
3min:TTFT = 排队 + prefill 计算 + (P/D 场景)KV 传输。**排队 → 容量/路由;prefill → chunk 切分/前缀缓存命中/CP;传输 → FP8 KV/多链(Ch9)。**
10min:分段测量方法(网关时间戳 + 引擎 trace,Ch20 L2);前缀命中的 TTFT 降幅(40-70%,Ch25 §25.3);双 SLO 场景下 TTFT 与 TPOT 的资源竞争(Ch22)。
追问:排队 90% 的 TTFT 是容量问题还是路由问题?怎么判?| Ch2/Ch9/Ch19/Ch20

**A15(★★★★)GPU 架构速答:SM / warp / HBM / SMEM 的关系?**
3min:GPU = SM 集合(H100 132 个);warp = 32 线程 SIMT 调度单位;数据路径 HBM → L2 → SMEM/L1 → 寄存器;**性能 = 数据搬运效率**(AI 视角,Ch10)。
10min:延迟靠并发掩盖(occupancy);Hopper 新硬件 TMA/WGMMA(FA3/DeepGEMM 的地基);消费卡 vs 数据卡的拓扑差异(Ch18 §18.1)。
追问:为什么"SMEM 小但快"?它解决什么问题?| Ch10

**A16(★★★★★)H100 / H200 / B200 各适合什么 serving 场景?**
3min:H200 = H100 带宽 +44% + 显存 +76% → **decode 类 +30-40%、长上下文并发 ×1.76**;prefill 不变。B200 = FP4 + 带宽 7.7TB/s → **MoE 权重 1/4、decode ×2**(生态爬坡期)。H100 = 均衡、生态最成熟。
10min:选型四步(容量→带宽→价格→生态,Ch19 §19.1);$/M token 口径对比;H800 的 NVLink 降速坑(400GB/s,Ch18)。
追问:H200 比 H100 贵 50%,什么负载下值?什么负载下不值?| Ch10/Ch19

**A17(★★★★)nsys 和 ncu 各看什么?什么时候用哪个?**
3min:nsys = 时间线(时间花在哪:kernel/gap/memcpy,进程级);ncu = 单 kernel(离 roof 多远:SOL/occupancy)。**顺序不能反:先 nsys 定位,再 ncu 深钻。**
10min:gap 分析(CPU 瓶颈 vs 通信等待,Ch20 §20.3);ncu 判读表(Memory 90% = memory-bound;两者都低 = occupancy);DCGM 第三层(时钟/降频)。
追问:nsys 抓 60s 的开销多大?会扰动系统吗?| Ch10/Ch20

**A18(★★★★)NCCL 是什么?为什么推理框架离不开它?**
3min:NVIDIA 集合通信库(all-reduce/all-to-all 等),自动选拓扑与算法。**TP 的每层 2 次 all-reduce、EP 的 all-to-all 都走它(或替代实现,如 vLLM 小消息 custom AR,Ch15 §15.4)。**
10min:ring/tree/NVLS 选择逻辑(小消息延迟/大消息带宽,Ch18 §18.3);busbw 判读(0.875×链路,§18.4);GDR;常见环境变量速查(附录 C)。
追问:怎么确认线上 TP8 走的是 NVLink 不是 PCIe?| Ch18

**A19(★★★★)什么是 goodput 最大化?给一个"吞吐已达标但 goodput 未达标"的例子。**
3min:goodput = SLO 约束下的有效吞吐。例子:大 batch 把吞吐推到 120%,但 TPOT p99 超 SLO 30% → goodput 实际低于小 batch 配置。**"达标"的吞吐是无效产能。**
10min:goodput 曲线的拐点定位方法(Ch22 §22.4 的 SLO 预算传导);调度器按 goodput 而非吞吐调参(Ch6 的 token 预算本质就是 goodput 旋钮)。
追问:两个 SLO 一松一紧时,goodput 的约束是谁?| Ch2/Ch6/Ch22

**A20(★★★★)从"流量(req/s + 长度分布)"到"卡数",完整推导一遍。**
3min:① 峰值 req/s × 平均输入长度 = prefill token/s;② 输出长度 × req/s = decode token/s;③ 单副本能力(实测压测:prefill token/s、decode 并发 × 1/TPOT);④ 卡数 = ceil(需求/单副本) × (1 + 故障域余量 + 突发余量 + 灰度副本)。
10min:P/D 配比(输入/输出 token 比,Ch9 §9.5);余量三部分(Ch23 §23.3);$/M token 成本闭环(Ch19 §19.4);与 Ch29 案例 10 的完整版本。
追问:"突发余量 30%"怎么定出来的?| Ch3/Ch19/Ch23

## B 框架深挖(45 题,主战场)

### B1-B5 PagedAttention

**B1(★★★★)PagedAttention 怎么实现?为什么"快"在哪?**
3min:KV 按固定 block(如 16 token)切块,物理块乱序分配,逻辑→物理用 block table 间接;attention kernel 按块迭代读取。**快 = 零碎片(内部碎片 ≤ 最后 1 块)+ 可复制(前缀共享)+ 可换出(swap),而不是 kernel 本身更快。**
10min:与操作系统虚拟内存的类比(请求=进程,token=页);block table 进 kernel 的方式(Ch12 §11 手写 kernel);prefix cache 靠块复制实现引用计数。
追问:为什么块不是越小越好?| Ch5

**B2(★★★★)block size 怎么选?16 vs 32 vs 64?**
3min:小 = 碎片小但 block table 大、kernel 块间接开销大;大 = 反之。**默认 16 通常是好的;实测差异 <2%(Ch25 §25.2 的验证结论)——它是"不是瓶颈"的参数,别在这上面花调优时间。**
10min:与 KV 量化(块对齐 scale)、prefix cache(块为复制单位)、P/D 传输(块为搬运单位)的耦合(Ch5/Ch9)。
追问:KV FP8 的 block scale 与 paged block 尺寸要一致吗?| Ch5/Ch8

**B3(★★★★★)前缀缓存的实现:哈希 block 还是 radix tree?各自的逐出策略?**
3min:vLLM:哈希 block(连续前缀的块哈希,LRU 逐出);SGLang:RadixCache(radix tree,树节点 = 公共前缀,子树共享)。**共享 = 引用计数,逐出 = 计数 0 且 LRU。**
10min:radix tree 的多分叉(不同后缀共享前缀)比哈希链更省;命中率对负载结构的敏感(逐字节相同,Ch25 §25.3 坑);逐出与 KV 压力的交互(抢占时先逐冷前缀,Ch22 §22.1)。
追问:流式对话每轮全量重发,prefix cache 命中的是哪一段?| Ch5

**B4(★★★★)PagedAttention 的代价(不只有好处)?**
3min:① block table 间接(kernel 多一层寻址,decode 小量);② 物理块不连续 → L2 局部性变差(对长 KV 的 attention 读取);③ 管理复杂度(分配器/引用计数/碎片器)。**代价在 decode 上是小量,换来的是显存效率与调度自由度——净收益巨大,但要知道代价存在。**
10min:与"连续 KV + 大 block"方案的取舍;FlashInfer 对 paged 布局的优化(Ch11 §11.3);P/D 场景下块布局必须 P/D 一致(Ch9 §9.2)。
追问:什么场景下你会放弃 paged 用连续 KV?| Ch5/Ch11

**B5(★★★★)KV 的 swap(swap-out 到 CPU)与 recompute 怎么选?代价各多少?**
3min:swap = KV 拷贝 PCIe(1GB ≈ 20-40ms 单程);recompute = 重新 prefill(32K ≈ 1-2s 单卡)。**短上下文 recompute 反而便宜;长上下文 + CPU 内存富余 → swap。vLLM 默认 recompute。**
10min:抢占的触发链(KV 压力 → 选 victim → 执行,Ch21 §21.2);被抢占请求恢复后的 TTFT 代价;抢占风暴的识别(Ch20 症状库"吞吐低延迟正常")。
追问:swap 的 KV 在 CPU 侧占多少内存?怎么和系统内存共存?| Ch6/Ch21

### B6-B12 vLLM v0 vs v1

**B6(★★★★)vLLM v0 为什么重写?v1 架构的核心变化?**
3min:v0 单进程、同步调度、CUDA graph 受限;v1 = **双进程(调度器独立 + GPU worker 异步)+ 事件驱动 step + 更干净的 scheduler/worker 接口 + graph 分桶成熟**。**本质:把 CPU 调度与 GPU 执行解耦,消除同步等待(Ch4 §4.4)。**
10min:双进程模型的数据流(请求事件 → 调度决策 → GPU step);为什么"双进程"而不是"多线程"(GIL + 调度确定性);v1 的 metrics/trace 改进(Ch20 的 L2 分段数据从哪来)。
追问:v1 的调度延迟量级?和 v0 差多少?| Ch4

**B7(★★★★★)v1 的"双进程模型"具体怎么工作?调度器进程里发生了什么?**
3min:主进程 = OpenAI API + 调度器(CPU,GPU 不参与);worker 进程 = 模型执行(每 step:组装输入 → 选 graph 桶 → 执行 → 回传采样结果)。**两进程异步:调度器排 step N+1 时,worker 跑 step N → CPU gap 消失(Ch12 §12.3 对策③)。**
10min:请求状态机(waiting → running → preempted → finished);token 预算分配在哪个进程;跨进程通信(共享内存/事件,量级 μs)。
追问:双进程后,调度器本身会不会成为瓶颈?| Ch4/Ch12/Ch20

**B8(★★★★)CUDA graph 在 vLLM v1 里怎么生效?哪些 step 进图?**
3min:decode step 按 **batch size 分桶**(1,2,4,8…512)各捕获一张图;运行时 pad 到桶 → 取图 replay。**KV 用 block table 间接寻址(图记"读表"不记"读块号")→ 不同请求共享同一张图。prefill 不进图(动态 shape)。**
10min:capture 成本(启动期秒级/桶)+ 每桶显存冗余;graph 逃逸的识别(Ch20 §20.3 nsys 特征);通信进图的判据(shape 静态,Ch15 §15.4)。
追问:为什么 decode 能分桶、prefill 不能?| Ch12

**B9(★★★★)vLLM 的采样在 GPU 上做什么?top-p / top-k 怎么融合?**
3min:采样 kernel(GPU):对 logits 做 top-k 截断 + top-p 累积 + 温度 + 重复惩罚,一次 kernel 出 token 与概率。**融合 = 避免 logits 在 GPU/CPU 间往返 + 多个小 kernel 的 launch(Ch12 §12.3)。**
10min:spec decode 的采样融合(Ch7 的 rejection sampling 在同一 kernel);structured output(受限解码:logits mask,Ch29 SGLang 题)。
追问:beam search 在推理框架里为什么不常用?| Ch4/Ch7

**B10(★★★★★)vLLM 的 custom all-reduce 是什么?为什么不用 NCCL?**
3min:decode 的小消息 all-reduce(≤~几百 KB)NCCL 的延迟地板高;vLLM 自研 **P2P 直连 + symmetric memory** 实现,小消息延迟 ~30-50μs vs NCCL 的 ~100μs+ 量级。**大消息仍走 NCCL——按消息大小双后端。**
10min:NVLink P2P 的直写(一卡写另一卡的 buffer,免中间规约);与 NCCL 的切换阈值;多节点时 custom AR 不可用(EP 的 all-to-all 走 DeepEP/NCCL,Ch16)。
追问:怎么验证线上确实在用 custom AR 而不是 NCCL?| Ch15

**B11(★★★★)vLLM 的 OpenAI 兼容层做了什么?流式响应的实现?**

### B13-B19 调度器

**B13(★★★★)waiting 与 running 队列的调度规则(vLLM v1)?**

**B14(★★★★★)token 预算(max_num_batched_tokens)本质是什么?**

**B15(★★★★)抢占(preemption)的完整流程与代价?**

**B16(★★★★★)调度器的"步"(step)粒度是什么?为什么 decode 步只有几 ms?**

### B27-B33 投机解码

**B27(★★★★)投机解码为什么"无损"?证明梗概。**

**B28(★★★★)推导投机解码的净加速公式;代入 γ=5, α=0.8, c_d=0.1 与 0.5。**

10min:α 的分布性(逐 token 几何分布,低 α 时 γ 浪费更多);tree attention 的收益(树节点数 = 真实验证成本);与 batch 的交互(B29)。

**B29(★★★★★)投机解码什么时候不 work?给三条判据 + 经验曲线。**

3min:**先问:长尾是结构性(热 expert/长 prefill/通信)还是容量性(排队)?结构性加卡 = p99 略降但根因还在(尖刺频率不变),成本翻倍(Ch22 踩坑框)。**判据:尖刺与负载的相关性(相关性低 = 结构性;排队主导 = 容量性,Ch22 §22.1/§22.2)。
10min:两类长尾的处置差异(结构性:三档 playbook,Ch22 §22.3;容量性:扩容 + shed,§22.3 过载级);加卡对 p50 与 p99 的不同影响(p50 降,p99 结构性成分不降);决策的量化(尖刺频率 × 幅度 vs 卡的成本,Ch22 §22.3 MoE 专项)。
追问:加 50% 的卡,p99 降 30% 还是 60%?怎么预判?| Ch19/Ch22

**E25(★★★★)过载 shed:拒绝的决策逻辑?**
3min:**shed 决策器 = 队列深度 + 请求预测耗时(输入长度 → prefill 时间估算)→ 超 SLO 预算的请求拒绝(429)或降级(降 max_tokens / 换小模型)(Ch22 §22.3)。**原则:**宁可拒绝 1%,不让 99% 慢**(p99 SLO 的数学含义);顺序:先拒长请求(预估值大),后拒短请求(Ch28 B25)。
10min:shed 与 SLO 预算的传导(网关按"副本剩余 SLO 预算"分流,Ch22 §22.3);降级 vs 拒绝的权衡(用户体验与成本);恢复后的回缩滞后(防锯齿,Ch19 §19.3)。
追问:shed 率 2%,SLO 达标,值得吗?怎么向业务解释?| Ch2/Ch22/Ch23

**E26(★★★★)SLO burn rate 告警怎么设计(双窗口)?**
3min:**燃烧率 = SLO 违反速率 / 预算;双窗口:快速(5min 窗烧 5% 月度预算 → 页人 P1)+ 慢速(1h 窗烧 0.9% → 工单 P2)(Ch22 §22.4)。**比固定阈值好:阈值在负载变化时误报/漏报,burn rate 自适应容量(容量翻倍后同程度恶化烧预算速度不同,§22.4)。
10min:TTFT 与 TPOT 各一套预算(双 SLO 两路告警,Ch28 E1);告警的抑制(同一根因的多指标告警聚合,Ch23 §23.2);burn rate 与 goodput 的关系(燃烧 = goodput 损失率,Ch2 E2)。
追问:月度预算 0.1%,5min 烧 5% 是什么概念(换算成请求数)?| Ch2/Ch22/Ch23

**E27(★★★★★)"结构性长尾"与"容量不够"的 p99 在指标上长什么样?**
3min:结构性:尖刺频率与负载**无强相关**(轻载也尖刺),p99/p50 比值波动大,尖刺时全请求或单请求成批(Ch22 §22.1 通信/throttle/热 expert 指纹);容量性:TTFT 主导(排队),**与负载正相关**,p99/p50 比值随负载单调升,TPOT 相对稳定(Ch20 §20.2 "TTFT 高"行 + §22.1 第 1 行)。

追问:给你 p99 时序 + 负载时序,怎么画"相关性图"做判定?| Ch20/Ch22

**E28(★★★★)SLO-aware 扩容:在队列爆之前扩容的触发器怎么设计?**
