## 使用方法(动笔前先读)

1. **时间盒**:面试一题 30-45 分钟。节奏 = 5min 复述需求+反问澄清 → 10min 容量估算+架构 → 15min 权衡 → 5min 留追问。本章每个案例按这个节奏写,练的时候也按这个节奏计时。
2. **假设必须标注**:每个数字标 [假设] / [实测] / [官方](Ch2 数据口径)。不标假设的设计在面试里是减分项——"你连这是估的还是测的都说不清"。
3. **开案例先问三件事**:输入/输出长度分布?SLO 是双 SLO 吗?硬件与卡数给定还是自选?**缺任何一件都先反问,再动手**——面试官给不出数字时,你替它假设并声明。
4. **公式工具链**:Ch3 (3-1)~(3-5) 容量链;Ch9 §9.2 KV 传输表;Ch13 (13-1) all-to-all;Ch14 (14-1)/(14-2) TP/PP 通信量。估算段全部从这里来。
5. **别追求"想到一切"**:好答案的标志是**有界**——明确说出"这一版架构不解决什么、什么信号出现时升级为哪个方案"(案例 1 的 P/D 与案例 3 的 CP 升级路径是范本)。
6. **与 Ch28 的分工**:Ch28 是"点"(单题快答),本章是"面"(跨章组合)。先 Ch28 后本章;Ch30 教你把案例里的数字讲成项目语言。

## 案例 1:100B+ MoE 生产级 serving(64 卡、TPOT p99 < 60ms、高并发)

### 1.1 需求(带数字)

- 模型 R(参考配置 [假设]):总参数 235B,激活 ~22B/token,94 层,hidden 4096,128 routed experts + 1 shared,top-8,GQA(kv_heads=8, head_dim=128),32K 上下文——量级对齐 Qwen3-235B-A22B 家族。
- 硬件:64× H100-80GB(SXM,NVLink 900GB/s/节点;节点间 8×NDR400(400Gb/s)IB,rail-optimized(聚合 ~50GB/s/卡))[官方口径]。
- 负载:峰值并发 ~500,平均上下文 4K,输入/输出长度比 8:2,前缀复用率 ~40% [假设]。
- SLO:TPOT p99 < 60ms;TTFT p95 < 3s(输入 ≤16K 桶)。
- 可用性:99.9%(月度,年停机预算 ~8.8h)。

### 1.2 需求分解

1. **权重是第一约束吗?** → 先算容量(1.3),架构在容量后面定,不是反过来。
2. **TPOT p99 < 60ms 很松**(decode 步 ms 量级)→ 主约束其实是**并发(KV 容量)+ p99 尖刺(热 expert,Ch13 §13.4)**。
3. **99.9% 排除"全集群单副本"**:单节点挂 = 全服务停(MTTR 10-20min,Ch19 §19.2),月故障 1-2 次就烧穿 8.8h → **必须 ≥2 个故障域**。

### 1.3 容量估算(Ch3 公式链)

| 步骤 | 计算 | 结果 |
|---|---|---|
| 权重(Ch3 §3.2 公式) | FP16 = 235B×2B;FP8 = 235B×1B | 470GB / 235GB |
| 集群总量 | 64 × 80GB | 5120GB |
| FP16 判定 | 470/5120 = 9%,权重不是第一约束 | **FP16 容量可行;选 FP8 是性能选择**(decode 权重读减半 + KV 减半 + prefill FLOPs ×2,Ch15 §15.1),过 Ch8 §8.4 质量门禁 |
| FP8 权重/卡 | 235GB / 64 卡 | 3.7GB/卡 |
| KV 池/卡 | 80×0.9 − 3.7 − 5(激活+NCCL) | ≈ 60GB/卡 |
| KV/token(全模型) | 2×94×8×128×2B (3-1) | 384KB/token;attention TP8 后 48KB/卡/token |
| 单请求 KV(4K 上下文) | 384KB × 4K | 1.5GB(全模型) |
| 并发上限(KV 口径,EP32 副本 32 卡) | 32×60GB / 1.5GB | **≈ 1280/副本**(KV 上限,非 goodput) |
| decode 步时 | 激活 22B FP8:每卡读 ≈ **2.6GB**(attention 稠密 TP8 ~2GB + routed 14B/EP32 ~0.4GB + shared TP8 ~0.2GB,无双重计数) | 2.6GB/3.35TB/s ≈ 0.8ms + all-to-all(低延迟模式,~百 μs 量级,Ch16 §16.2)+ attention KV → **步 ~2-4ms** |
| TPOT 预算 | p50 ~2-4ms;p99 含热 expert 尖刺(×3-5 量级) | **< 60ms 有 10 倍以上余量** ✓ |

**结论:FP8 下容量充裕;约束排序 = ① 故障域(可用性)② 热 expert p99 ③ KV(富余)。卡数不是瓶颈,结构才是。**

### 1.4 架构设计(参考)

```
64 卡 = 8 节点
  ├─ 副本 1:4 节点 = attention TP8(节点内 NVLink)+ expert EP32(跨节点)
  └─ 副本 2:同副本 1(DP = 2)
网关:前缀感知一致哈希(软亲和,命中且不过载才走)+ 副本均衡(Ch19 §19.3)
引擎:vLLM/SGLang + FP8 权重 + FP8 KV;chunked prefill,token 预算 8K(长短 8:2 负载)
量化:FP8(不是 W4——见 1.5)
```

关键映射:**"节点内快、节点间慢"的拓扑 → TP 落在 NVLink 域、EP 跨节点**(Ch16 §16.4 生产形态;attention 稠密 GEMM 适合 TP,expert 数据相关 GEMM 适合 EP)。

### 1.5 权衡讨论

- **为什么不是纯 EP(attention 也切 expert 式)?** attention 是稠密 GEMM,TP 通信规整(all-reduce,Ch14 (14-1));EP 的 all-to-all 数据相关、延迟主导(Ch13 §13.2)——稠密部分不该用数据相关的切法。
- **为什么 TP 不跨节点?** Ch14 §14.2 数字链:70B 级每步 2.5MB all-reduce,NVLink 50-100μs vs IB 50GB/s 下 1-2ms(×18)→ TP 天花板由拓扑画,不由算法画。
- **1 副本 EP64 vs 2 副本 EP32?** EP64:KV 上限 2×(2560)、步时略优(all-to-all 消息小),但**故障域 = 全集群**,与 99.9% 直接冲突。EP32×2:KV 上限 1280/副本(目标 500 并发富余),故障域 4 节点 → **选 EP32×2,余量留给故障域**。
- **FP8 vs W4A16?** W4 再吃 ~2× 带宽(decode),但 4bit MoE 质量风险高(热 expert 精度分配,Ch8 §8.5)、评估成本高。本案 SLO 富余 → **FP8 首发,W4 列为二期实验(挂 Ch8 §8.4 门禁)**。
- **P/D 为什么不开?** Ch9 §9.3 判据:32K 上下文 + 500 并发 + TTFT 3s(松)→ chunked prefill 已够;P/D 是 TTFT 收紧到 ~1s 或长请求占比 >30% 时的升级项(信号监控挂着,见案例 5)。
- **热 expert 是内建项不是优化项**:EP32 → 每卡 ~4 个 expert,单 expert 偏斜直接 = p99(案例 8 的治理必须在上线前就位,离线热度统计 + 静态放置)。

### 1.6 预期追问

1. **EP32 的 all-to-all 会带宽主导吗?**(Ch13 (13-1):decode 每步总量 = 500×1×8×4096×1B(FP8)≈ 16.4MB/层,÷31 对端 ≈ 0.5MB/对端 → 仍是**延迟主导**;batch 涨到 ~2000 才转向带宽主导,届时步时 scaling 要实测,Ch16 §16.4 踩坑框)
2. **一个节点挂了?**(案例 9:容量 −1/2,10-20min 恢复;99.9% 是否仍达标 = 负载 × 时间 的数学)
3. **并发涨到 1000 怎么办?**(先查 KV 上限 1280 够不够 → 再查 all-to-all 主导模式翻转 → 再考虑 DP 加副本;顺序不能反,Ch28 D4)
4. **为什么不用 H200?** 本案 decode 富余、成本导向 → H100 够用;若 TPOT 收紧到 30ms 或并发 1500,H200 的 +44% 带宽 +76% KV 才进入决策(案例 4/10 的 $/M 口径)

### ◆ 评审点

- [ ] 容量估算**先于**架构,且算清了权重不是第一约束(FP16 9% / FP8 5%,第一步就分胜负)
- [ ] 故障域与 99.9% 的权衡被显式写出(EP64 单副本为什么被否)
- [ ] 热 expert、P/D 升级信号、W4 二期**明确列为开放项**,而非假装想到一切
- [ ] 所有估算数字带 [假设]/[实测] 标注

## 案例 2:低延迟 chat(p99 TTFT < 50ms、100 req/s、短输出)

### 2.1 需求(带数字)

- SLO:**p99 TTFT < 50ms**(含排队);TPOT p95 < 30ms [假设]。
- 负载:峰值 100 req/s;输入平均 512 token(系统提示词 ~200 全员共享 + 用户 ~312);输出平均 128 token;输入 p99 ~2K [假设,需向业务确认]。
- 硬件:2 节点(16× H100-80GB)预算 [假设,需确认]。
- 模型:**自选**(需求没给——这是本案的设计自由度,也是第一个决策点)。

### 2.2 需求分解

1. **TTFT 50ms 的预算拆分**:TTFT = 排队 + prefill。p99 口径下排队必须 <5ms(排队对 p99 是乘法放大)→ **prefill 容量必须 ≈ 匹配到达率,不能有系统性排队**。
2. **prefill 需求**:100 req/s × 512 tok = 51.2K prefill tok/s(前缀命中 0% 口径);系统提示词 200 tok 全员共享 → **前缀命中 40-70% 是常态**(Ch25 §25.3 量级)→ 有效 prefill 需求 15-30K tok/s。
3. **decode 需求**:100 × 128 = 12.8K tok/s——很小。
4. **结论:本案是 prefill 容量 + 前缀命中的问题,不是 decode 问题**。模型大小直接决定 prefill FLOPs → **模型选型是第一决策**。

### 2.3 容量估算(Ch3 公式链 + 实测假设)

| 候选 | prefill 512 tok(单 H100,FP8) | 8K 节点组 prefill 能力(量级) | 判定 |
|---|---|---|---|
| 70B TP8 | ~15-20ms(Ch9 §9.3:8K≈250ms 回推) | ~50-60 req/s(512 tok 口径) | **p99 50ms 不可达**(p99 输入 2K 时单条 60-80ms 已超 SLO) |
| 14B TP1-2 | ~3-5ms | ~200-300 req/s(单卡) | ✓ 富余 |
| 7B TP1 | ~2-3ms | ~300+ req/s(单卡) | ✓✓ |

(数字 [假设+实测量级]:以 Ch25 的 bench 方法在候选模型上实测校准;面试现场给量级 + 说明"需要实测",不给伪精确。)

**关键判断:p99 TTFT 50ms 在 100 req/s 下要求"任何一条请求的 prefill < 45ms 且几乎零排队"。** 70B 即使全命中前缀,未命中的 312 tok 也有 ~10ms,但 p99 的 2K 长输入(命中后仍 ~1.8K 要算)→ 70-150ms,超 SLO 3 倍。**要么模型降档,要么 SLO 改桶**——这是本案必须向业务摊牌的点。

### 2.4 架构设计(参考)

```
模型:14B FP8(质量-延迟折中;7B 备选,质量门禁 Ch8 §8.4)
部署:1 节点 8 卡 = 4-6 个 DP 副本(TP1-2)+ 1 节点备(故障域 1 节点,99.9% 单节点不满足 → 双节点 DP,或接受 99.95% 口径)
前缀缓存:必开(系统提示词 = 100% 共享前缀)
路由:前缀感知一致哈希 → 同会话/同系统提示词落同一副本(命中率最大化,Ch19 §19.3)
调度:token 预算 2K(短输出负载,保护 p99);max_num_seqs 按 KV 上限的 80%
投机解码:关(batch 高 + 输出短,Ch7 §7.4 双条件不满足)
shed:到达 >120 req/s 或队列 >0 持续 10s → 429(保 TTFT 预算,Ch22 §22.3)
```

### 2.5 权衡讨论

- **模型降档 vs SLO 改桶**:如果业务坚持 70B 级质量,正确答案不是硬扛 50ms,而是**把 SLO 改成桶化口径**:"p50 TTFT < 80ms(命中前缀)/ p95 < 300ms(未命中长输入)"——用 Ch2 的分桶方法把"不可能"翻译成"可能的两个桶"。面试里这一句话展示的是**需求工程**,不是 GPU 知识。
- **DP vs TP**:小模型 TP 只为装进单卡;多副本用 DP(零通信,故障域 = 1 节点,扩容粒度 = 1 副本)。14B FP8 单卡装下 → **TP1 起步**,不浪费 NVLink。
- **为什么不用 P/D**:Ch9 §9.3 判据全不满足(短上下文 + 中负载 + 单 SLO 主导)→ 多付一套传输层运维换 0 收益。
- **前缀命中率的地板**:命中 0%(缓存被逐出/路由乱)时 TTFT 翻倍 → 监控命中率 <30% 告警(Ch23 §23.2 系统级指标);路由哈希环变动(副本上下线)会短暂打散命中 → 软亲和 + 预热期降权。
- **双节点故障域**:1 节点挂 = 容量 −50%,100 req/s 直接 shed → 99.9% 不达标(年 8.8h 预算 vs 节点故障 1-2 次×恢复时间)。若业务要 99.9% → 3 节点(挂 1 剩 2/3 > 100% 需求)或接受"99.9% 不含节点级故障"的口径声明。

### 2.6 预期追问

1. **怎么证明 p99 50ms 可达?**(TTFT 三段分解监控:排队/prefill/网络,Ch20 L2 分段;压测用真实负载画像(长短混合 + 前缀 50%),不用随机文本,Ch2 A8;goodput 曲线在 100 req/s 处的位置,Ch27 §27.5 方法)
2. **输入 p99 = 8K 怎么办?**(桶化 SLO 或长请求单独池(小模型池 + 大模型池双池,Ch9 §9.5 双池网关的短版本);8K prefill 14B 单卡 ~50-100ms → 进 p99 桶,不进主 SLO 桶)
3. **100 req/s 涨到 300?**(DP 加副本线性扩,零通信;先查前缀命中率是否随副本数下降(哈希环变动),再扩)
4. **为什么不用小模型 + 投机?**(输出 128 token < 2γ 摊销失败 + batch 高 → 双条件不满足,Ch7 §7.4;开了反而掉吞吐,白付 draft 算力)

### ◆ 评审点

- [ ] 第一个决策是**模型选型**且给出了"70B 不可达"的定量论证(不是背配置)
- [ ] TTFT 预算被拆成 排队/prefill/网络 三段,各段有预算
- [ ] 主动提出"SLO 改桶"的需求工程选项(展示与业务对话的能力)
- [ ] 前缀命中率被当作**一等公民指标**(地板 + 告警),而不是功能开关

## 案例 3:长上下文 1M RAG serving(KV 成本、prefill CP、检索命中前缀复用)

### 3.1 需求(带数字)

- 模型:MLA 1M(DeepSeek V3 系):总 671B,激活 ~37B/token,MLA(512 维 latent + 64 维 rope,K/V 共享,61 层)→ 全模型 ~70KB/token(BF16)/~35KB(FP8,Ch17 §17.3),1M 上下文。
- 负载:RAG,峰值 5 req/s;平均输入 300K(p95 ~800K,max 1M);平均输出 1K;**检索文档集高度复用 → 前缀复用率 30-60% [假设,需从网关日志画像]**。
- SLO:TTFT p95 < 60s(1M prefill 是分钟级任务,SLO 松);TPOT p95 < 80ms。
- 硬件预算:32 节点(256× H100-80GB)[假设]。

### 3.2 需求分解

1. **两段结构**:prefill(300K-1M 计算,重)+ decode(1M KV 驻留,重)→ **P/D 分离是天然解**(Ch9 §9.3 三判据:长上下文 ✓ + 高负载 ✓ + 双 SLO ✓)。
2. **KV 不再是第一约束(修正 MLA 数字后)**:1M × 70KB(BF16)/ 35KB(FP8) = 70GB / ~35GB 每请求(全模型)→ TP8 单副本 4.4GB/卡(FP8)→ 并发 ~13(60GB 池,Ch17 §17.3)→ **KV 不再逼 CP decode**(P 侧 CP 仍是速度选项)。
3. **prefill 是计算约束**:300K prefill = 2×37B×3e5 ≈ 2.2×10¹⁶ FLOPs;1M = 7.4×10¹⁶(Ch17 §17.1)→ 单卡 ~100s(1M)/ ~30s(300K,量级)→ **P 侧必须 CP 摊序列(速度,非容量)**。
4. **前缀复用是 RAG 的隐藏杠杆**:同一文档集被反复检索 → 检索块成为共享前缀 → P 池前缀缓存命中 40-60% = **有效 prefill 需求减半**(比任何 kernel 优化都大)。

### 3.3 容量估算(Ch3 公式链 + Ch17 §17.3 回代)

| 项 | 计算 | 结果 |
|---|---|---|
| prefill FLOPs | 300K:2.2×10¹⁶;1M:7.4×10¹⁶ | 单卡 ~30s / ~100s(量级,FP8) |
| P 组形态 | CP4 × TP8(32 卡,4 节点) | 300-400K tok/s/组(300K 有效口径,[估算];Ch17 §17.1/§17.3) |
| P 池规模 | 5 req/s × 300K × (1−50% 命中) ≈ 750K 有效 prefill tok/s ÷ 300-400K/组 | **3 组(12 节点)**:挂 1 组剩 2 组(750K/600-800K,TTFT p95 60s 仍有余量) |
| D 副本形态 | TP8:KV/卡 = 35GB/8 ≈ 4.4GB(FP8,全模型 70GB/~35GB) | 并发 ~13(60GB 池,Ch17 §17.3:KV 不再逼 CP decode) |
| D 池规模 | 5 req/s × 1K = 5K tok/s;~13 并发/副本(队列主导,decode 相 ~20-25s/请求,[估算]) | **3 副本(3 节点)**:挂 1 剩 2/3 |
| KV 传输 | P(CP4×TP8)→ D(TP8):序列维 all-gather + reshard | 35GB/8 = 4.4GB/链,~0.1-0.3s/请求;多链 + GDR |

**总计:12 + 3 = 15 节点 ≤ 32 节点预算**(余量 17 节点 = 季度增长 + N+1 故障域)。

### 3.4 架构设计(参考)

```
[网关:前缀感知路由(检索块哈希→P 组亲和)+ 长度路由]
   ├─ P 池(prefill-only,12 节点 = 3 组 CP4×TP8)
   │    MLA + CP(Ring,跨节点,Ch17 §17.2)+ 前缀缓存(检索块共享)
   │    传输完成 → KV 释放(池周转快)
   └─ D 池(decode,3 节点 = 3 副本 TP8)
        FlashDecoding split-KV(1M 必须,Ch11 §11.4)+ MLA 特化 kernel
        P→D:序列维 all-gather + reshard(4.4GB/链,~0.1-0.3s);槽位预留(Ch9 §9.2 同步协议)
KV:全链路 FP8 latent;质量门禁(长上下文 8K/32K/1M 三档退化,Ch8 §8.4)
```

### 3.5 权衡讨论

- **D 侧为什么选 TP8 而不是 CP4×TP8(旧结论"KV 容量逼 CP decode")?** 修正 MLA KV 数字后(1M = ~35GB(FP8)全模型,TP8 4.4GB/卡,并发 ~13),KV 容量不再逼 CP decode——D 侧选 TP8(1 节点故障域,布局简单);P 侧 CP4 是速度/故障域选项(300K-1M prefill 单卡 ~30-100s,CP4 组 ~1-3s),不是容量必需。代价:P(CP4×TP8)→ D(TP8)需序列维 all-gather + reshard(4.4GB/链 ~0.1-0.3s)——在 p99 预算内(传输 <5% TTFT)。**本案决策链要连着讲:KV 数字修正后,"CP decode 是容量必需"的旧结论被推翻——先算数,再定架构。**
- **前缀缓存放在 P 池而不是 D 池**:前缀省的是 prefill 计算,不是 decode 驻留;D 池要的是完整 KV。路由按"检索块哈希"而不是"请求哈希"(同一文档集的不同问题应落到同一 P 组,Ch19 §19.3 的前缀感知在 RAG 的具体化)。
- **业务侧杠杆排在架构前面**:RAG top-k 从 50K 降到 30K 检索块 = prefill 需求 ×0.6,质量门禁通过后**比加任何硬件都便宜**——先和业务谈这个,再谈卡数。
- **冷启动**:新文档集上线时前缀命中率 0% → P 池瞬时 2× 需求 → 运维动作:热门文档集**预热**(上线前把前缀灌进 P 池缓存,一次性 prefill 成本换命中率)。
- **TTFT 60s 的构成**:P 侧排队(<5s,3 组有余量)+ prefill(1-3s,300K,命中后更短)+ 传输/reshard(0.1-0.3s)+ D 侧排队(均值 ~10-15s [估算],3 副本队列主导)→ SLO 满足且有余量;**真正的风险是 p99 长输入(1M 全量,prefill ~3-6s + 队列),不是均值**。

### 3.6 预期追问

1. **为什么 prefill 不用 TP16?** TP 天花板 = NVLink 域(Ch14/Ch15);序列维切分用 CP,跨节点走 RDMA(P2P,延迟主导,Ch17 §17.2 口诀:节点内 Ulysses、跨节点 Ring)。
2. **检索块全部是新文档(命中 0%)?** P 池需求 ×2-2.5 → 余量节点顶上;若持续 >2 周 → 画像漂移,重新容量规划(Ch23 §23.4 回归)。
3. **D 池某副本并发降到 2(KV 压力)?** P/D 后 D 池纯 decode,抢占罕见;先查前缀/长短混合(1M 请求挤占 300K 的 KV,Ch3 (3-3) 回代)→ 网关按输入长度分桶路由(长进专门副本)。
4. **1M 单请求的 $ 成本?(接案例 10)** prefill 2.2-7.4×10¹⁶ FLOPs 摊到 ~1-4 节点·秒 + decode 1K token ~数秒 → 单请求成本是 8K 对话的 100-500 倍 → **定价模型必须按输入长度分桶**(RAG 业务的核心成本结构)。

### ◆ 评审点

- [ ] 两段结构(prefill 计算 / decode KV)被分别估算,没有混在一起
- [ ] "P 侧 CP + D 侧 TP8(引入 reshard 成本)"与"P/D 同布局(更大故障域)"的权衡被显式论证(而不是默认任一方)
- [ ] 前缀复用被当作容量参数(不是功能),且有冷启动/预热方案
- [ ] 主动提出业务侧杠杆(top-k)优先于架构侧

## 案例 4:成本降 10×(H100 FP16 基线 → 量化 + P/D + 硬件选型组合拳)

### 4.1 需求(带数字)

- 基线:70B 稠密 GQA,FP16,TP8 × 8 副本(64× H100-80GB),服务混合负载(8:2 长短,前缀命中 ~40%),**实测 $/M token ≈ $7 [假设基线,Ch25 实测法]**(池 goodput ~5K tok/s(SLO 约束),64×2×278÷5K ≈ $7/M,Ch19 §19.4 公式)。
- 目标:**$/M token 降 10×(→ ~$0.7)**,2 个季度内。
- 硬约束:质量门禁(Ch8 §8.4 流程,各任务 Δ 不超阈值);SLO 不变(p95 TTFT 2s / p99 TPOT 100ms);可用卡池不变(64 卡,不新购)。

### 4.2 需求分解

1. **$/M = (卡数 × $/卡时) ÷ (实测 goodput tok/时 ÷ 10⁶)** → 10× = 各杠杆乘积。每个杠杆必须**单独可验证**(A/B,Ch27 §27.5 方法),不允许"打包上线看总数"。
2. 杠杆清单与量级(保守口径,[假设+实测量级]):

| 杠杆 | 机制 | goodput 乘数 | 代价/风险 |
|---|---|---|---|
| ① FP8(权重+KV) | decode 权重读 ÷2(步 ~×1.6-1.8);prefill 算力 roof ×2;KV 池 ×2 抬并发 | **×1.5-1.8** | 质量门禁(KV FP8 长尾退化,Ch8 §8.4) |
| ② P/D 分离 | decode 池纯 decode(无 prefill 尖刺、无 KV 池竞争)+ 双池独立扩缩 | **×1.2-1.4** | 两套运维 + KV 传输层(Ch9) |
| ③ 负载侧:前缀缓存 + 前缀感知路由 | 有效 prefill ÷1.5-2;TTFT 余量 → batch 上调 → goodput 再 +10-20% | **×1.2-1.4** | 命中率依赖路由(哈希环变动,Ch19 §19.3) |
| ④ W4A16 decode 池 | decode 权重读 140GB→40GB(步 ~×2-2.5);prefill 保持 FP8 | **×1.3-1.6**(decode 占 ~80% 时间) | 4bit 台阶粗,质量风险最高(Ch8 §8.5) |
| ⑤ H200 换 decode 池 | 带宽 +44%(decode +30-40%)+ KV +76%(并发 ×1.76) | KV-bound 负载 **×1.3 左右**;卡价 ×1.5 → **$/M 近持平** | 只在 KV-bound 时净赚(Ch19 §19.1 判据) |
| ⑥ B200 NVFP4(窗口期) | 权重 1/4 + 7.7TB/s:decode 再 ×1.8-2;pilot 起步 | pilot 20% 池:整体 **×1.15-1.3** | 生态爬坡(C26 窗口期:kernel/量化工具未成熟) |

3. **乘积**:①×②×③ ≈ 1.7×1.3×1.3 ≈ **2.9×(纯 Hopper 软件栈的第一层)**;+④ ≈ **4×**(Hopper 上的现实天花板);+⑥ 全池 ≈ **7-8×**;10× 需要 ⑥ 全池 + 负载稳定 + 质量零退化——**"10× 是硬件代际 + 全假设成立的乘积,不是纯工程优化能给的"**。

### 4.3 架构设计(参考:分季路线)

```
Q1(稳赚层):  ① FP8 全池 + ② P/D(decode 池:8K-32K 负载)+ ③ 前缀路由
             目标 $7 → $2.4(×2.9);每步 A/B 门禁 + 质量门禁 + 5% 灰度(Ch23 §23.4)
Q2(激进度量层):④ W4A16 只上 decode 池(prefill 保持 FP8:4bit 在 compute-bound 侧收益小、
             风险大,Ch8 §8.5)+ ⑤ decode 池换 H200(若容量是 KV-bound)
             目标 $2.4 → $1.5-1.7(×4 累计)
Q3(窗口期层): ⑥ B200 NVFP4 pilot 20% 池 → 质量/性能双门禁 → 扩 50% → 全池
             目标 $0.9-1.1(×7-8);10× 条件触发(见 4.5)
```

### 4.4 权衡讨论

- **为什么 W4 只上 decode 不上 prefill**:prefill compute-bound,吃的是指令级 2×(FP8 已给);W4 的带宽收益在 decode(memory-bound)。且 4bit 质量风险集中在长输出(误差累积)→ **decode 侧输出长 = 风险高,必须任务级 benchmark 全过(Ch8 §8.4 的 ②③ 项)**。
- **H200 在本案是"条件杠杆"不是"必选项"**:若 P/D 后 decode 池已 KV 富余(并发不是约束),H200 的 +76% KV 无收益,卡价 ×1.5 纯亏(Ch28 D34 判据回代)。上线顺序:先 ①②③ 跑一个月看 decode 池 KV 使用率,>80% 才换。
- **B200 窗口期的双向风险**:早 = 吃红利(FP4 kernel 自写有真实收益,Ch12 §12.4 决策清单);晚 = 红利被库吸收(cuBLAS 支持 per-block scale 后自写收益归零)。pilot 20% 是对冲,不是赌。
- **10× 的触发条件(向管理层承诺的话术)**:"7-8× 是工程承诺(有 A/B 数据);10× 的条件承诺 = B200 全池 + 负载画像稳定(输入/输出比漂移 <±20%)+ 质量零门禁失败"——**把条件亮出来,比报一个 10× 的数字可信得多**。
- **常被 CFO 追问的修正项**:① 利用率(名义 goodput → 实测打 5-8 折,Ch19 §19.4);② 峰谷(夜间空闲卡也是成本 → 混部/缩容,Ch19 §19.3);③ P/D 后两个池的利用率要分别报(不能平均)。

### 4.5 预期追问

1. **哪个杠杆最可能不达?**(排序:④ W4 质量门禁失败概率最高(4bit + MoE/长输出);⑥ 生态滞后次之;①②③ 有 Ch25-27 实测背书,风险最低。答法:给概率 × 影响,并说"所以路线是稳赚层先行")
2. **负载从 decode 重变 prefill 重(如 RAG 上线),重算?**(W4 贡献减半(×1.3→×1.1),H200 变亏,FP8 的 prefill ×2 变主收益 → 重跑 4.2 的表,这就是"容量规划是季度动作"的实例,接案例 10)
3. **质量门禁失败(某任务掉 3%)怎么办?**(该任务回退 FP8,按租户/任务混合精度路由——精度分配 = 流量 × 敏感度,Ch8 §8.5;不是全盘回退)
4. **$/M 报给 CFO 的口径?**(分桶报:短对话桶 $/M vs 长文档桶;含利用率折扣;附 goodput 定义(SLO 内),Ch2 (2-5))

### ◆ 评审点

- [ ] 10× 被**分解成可单独验证的乘数**,每个乘数有机制解释(不是"优化了 10×")
- [ ] 明确说出 Hopper 软件栈的现实天花板(~4×),硬件代际是最后一个乘数
- [ ] 每个杠杆挂了质量门禁 + A/B + 灰度三重验证(工程纪律)
- [ ] 10× 被表述为"条件承诺"并列出触发条件(管理沟通能力)

## 案例 5:P/D 分离集群与动态配比(KV 传输链路、网络预算)

### 5.1 需求(带数字)

- 模型:70B GQA(80 层,kv_heads=8,head_dim=128,32K 上下文)——用 Ch9 的已知数字精算。
- 负载:峰值 200 req/s;输入平均 8K / 输出平均 512(输入/输出 token 比 ≈ 15.6:1);长短混合 8:2。
- SLO:双 SLO(p95 TTFT < 2s / p99 TPOT < 100ms)。
- 硬件:40 节点(320× H100-80GB),每节点 8×NDR400(400Gb/s)IB,rail-optimized(聚合 ~50GB/s/卡)[假设]。
- 要求:设计 P/D 分离集群 + **动态配比**机制,并给出 KV 传输链路与网络预算。

### 5.2 需求分解

1. P/D 判据复核(Ch9 §9.3):长上下文(8K 均值、p99 32K)✓ + 高负载(200 req/s,排队主导 TTFT)✓ + 双 SLO ✓ → **值得**。
2. 两个结构性冲突必须解决:KV 池竞争(长 prefill 挤 decode 并发)+ 扩缩容不对称(输入/输出比 15.6:1,P/D 需求比 ≠ 1:1)。
3. **网络预算是本案特有约束**:KV 传输与 NCCL 集合通信共享 IB → 不隔离 = 随机尖刺(Ch28 D33)。

### 5.3 容量估算(Ch9 §9.2 表 + Ch3 公式回代)

**KV 传输精算**(70B GQA,TP8 一致布局,P、D 各 rank 传自己的分片):

| 上下文 | KV/请求(全模型) | KV/分片(TP8,P/D 同布局) | 单链 @50GB/s | FP8 KV(分片减半) |
|---|---|---|---|---|
| 8K | 2.56GB | 0.32GB | **~6ms** | ~3ms |
| 32K | 10.2GB | 1.28GB | **~25ms** | ~13ms |
| 128K | 40.9GB | 5.12GB | **~100ms** | ~50ms |

传输只占 prefill 时间 2-4%(8K:6ms vs 250ms@TP8,Ch9 §9.3 定量例;128K:单链 ~100ms vs prefill ~3s,FP8 再减半)→ 8K 负载下仍**值得**(收益主要是结构隔离,不是省传输);128K 请求传输也只 2-4%(per-rank 分片口径)→ FP8 + 多链仍是标准做法(p99 保护 + NCCL 争抢,Ch18 §18.4),不是容量必需;案例 7 的 CP 场景另有 reshard 份额(回全模型口径)。

**P/D 配比(Ch9 §9.5)**:
- 输入需求:200 × 8K = 1.6M prefill tok/s;输出需求:200 × 512 = 102.4K decode tok/s。
- 单副本能力(实测假设,Ch25 方法):P 副本(TP8)≈ 8-16K prefill tok/s/卡(TP8 副本 ≈ 64-128K tok/s,8K chunk 步);D 副本(TP8)≈ 200 并发 × 1/100ms ≈ 2000 decode tok/s(SLO 内)。
- 起步配比:P = 1.6M/12K ≈ **134 卡 ≈ 17 节点**;D = 102.4K/2K ≈ **51 副本… 重算:102.4K tok/s ÷ 2000 tok/s = 51 副本 × 8 卡 = 408 卡 > 预算 320 卡**。
- **结论:320 卡装不下 200 req/s 峰值 → 要么 SLO 降级、要么 shed 15-30% 峰值、要么加卡/上 H200(decode 池,KV-bound,并发 ×1.76,Ch19 §19.1)。** 面试里这一步"装不下"的发现是加分项——先算账再画架构。
- 修正方案:decode 池换 H200(并发 ×1.76 → 需 ~29 副本 ≈ 232 卡)+ P 池 96 卡(12 节点,40% 前缀命中 [假设]:1.6M×0.6 = 960K tok/s ÷ 10K tok/s/卡;0% 命中则 134 卡或 shed ~30% 峰值)≈ **328 卡 ≈ 预算内**(H200 溢价计入案例 4 的 $/M 口径)。

### 5.4 架构设计(参考)

```
[网关:长度路由(输入 >16K → 长池)+ 双池队列监控 + 429 shed]
   ├─ P 池(12 节点,TP8 × 12):chunked prefill(8K chunk),前缀缓存
   ├─ D 池(23 节点,H200,TP8 × 23):纯 decode,槽位预留(Ch9 §9.2)
   └─ 短请求一体池(可选,Ch9 §9.5 双池网关):输入 <2K 的请求走一体副本
        ——省掉 KV 传输 hop,短请求 TTFT 更稳(8K 以下 P/D 收益本就薄,B41 判据)
KV 链路:NIXL 类 block 级搬运(GDR zero-copy)+ FP8 + 8 链并行
网络隔离:每节点 8 口 NIC → 1-2 口专用 KV(与 NCCL 集合通信分口,Ch28 D33)
        或 QoS:NCCL 高优先 DSCP,KV 走低优先(不能分口时,Ch18 §18.4)
动态配比:
  信号:P 池 waiting 队列深度 + D 池 running 饱和度(分钟级)
  动作:K8s 独立扩缩 P/D 池(gang 副本为粒度,前置时间 ~5-10min,Ch19 §19.3)
  防抖:扩缩回缩滞后 30min(burn rate < 0.1% 持续,Ch22 §22.4)
  稳态比:P:D ≈ 96:232 ≈ 1:2.4(卡口径,H200 修正 + 40% 命中假设)
```

### 5.5 权衡讨论

- **短请求为什么不走 P/D**:8K 以下 KV 传输 8-50ms vs 一体池省掉的 1 个 hop + 槽位预留复杂度 → P/D 收益薄,还多付运维(Ch9 §9.3 判据的反面:短上下文 + 中低负载 → chunked 已够)。双池网关 = "短走一体、长走分离",按输入长度切。
- **P 超调度的成本**:P 完成 prefill 但 D 池拒收(满)→ 这次 prefill 白算(浪费 FLOPs)+ KV 作废 → **P 池调度必须看 D 池槽位余量**(网关或 P 调度器订阅 D 池状态,Ch9 §9.2 同步协议的失败语义,B42)。
- **KV 传输与 NCCL 抢口的三种隔离**(成本递增):① QoS DSCP 分级(零硬件,偶发尖刺残留)② 分口(1-2 口专用,推荐)③ 错时传输(P/D 池调度错峰,调度层复杂)——8 口节点选 ②,4 口节点选 ① + 监控 per-NIC 吞吐(Ch18 §18.4 带载基线)。
- **动态配比为什么不是"实时"的**:gang 副本调度 + 模型加载前置时间 5-10min → 动态 = **分钟级跟随 + 流量预测提前量**(Ch22 §22.4 的 SLO-aware 扩容);秒级需求用池内 token 预算吸收(chunk 调小 = P 池内"软配比")。
- **P/D 后全局 goodput 变成跨池指标**(B44):网关层要同时看两池队列与 SLO 预算——监控看板从"每引擎一张"变"两池 + 网关一张"(Ch23 §23.2 的 P/D 变体)。

### 5.6 预期追问

1. **P 池快、D 池慢,瓶颈段怎么测?**(分段时序:网关入池时间戳 → P 完成时间戳 → D 开始时间戳(Ch20 L2 跨池版);瓶颈 = 时间戳差值最大的段;P 快 D 慢的典型 = D 池 KV-bound → 查 H200 是否到位/并发是否到顶)
2. **D 池 1 节点挂?**(容量 −1/23 ≈ 4%,SLO 不变;in-flight 请求语义 = 客户端幂等重试 + 前缀命中降重试代价,Ch21 §21.4;恢复 10-20min,案例 9)
3. **输入/输出比从 15:1 变 4:1(长输出业务上线)?**(P:D 需求比翻转 → P 池缩、D 池扩;这就是"动态配比"存在的理由,稳态比公式重算;若 D 池 H200 不够 KV → 上 FP8 KV 先撑)
4. **为什么不用 4 池(P 短/P 长/D 短/D 长)?**(每多一池 = 一份运维 + 一份路由复杂度;双池网关已覆盖 80% 场景,第三池等"短长混合 SLO 冲突实测出现"再加——**池的数量由 SLO 冲突矩阵决定,不由美学决定**)

### ◆ 评审点

- [ ] 先算账发现"320 卡装不下峰值",并给出修正(H200/shed/SLO 降级三选一),而不是硬塞
- [ ] KV 传输精算用了 Ch9 的表 + 多链/FP8 修正,网络预算有分口/QoS 方案
- [ ] P 超调度成本(白算 prefill)被识别,且调度依赖 D 池槽位状态
- [ ] 动态配比的"分钟级 + 预测提前量"边界说清楚(不是秒级实时)

## 案例 6:多租户 SLO 隔离(noisy neighbor、KV 隔离、过载 shed)

### 6.1 需求(带数字)

- 租户 A(高优,交互):峰值 100 req/s(持续 ~50 req/s),输入 ≤8K,输出 ≤512;p95 TTFT < 500ms,p99 TPOT < 100ms;**违约赔付**。
- 租户 B(批处理,长任务):峰值 200 req/s,输入 32K,输出 4K,p95 TTFT < 30s(best effort,无赔付,允许错峰)。
- 硬件:64 卡(8× H100-80GB 节点),现有 70B FP8 模型,不新增硬件(预算另算,先做架构)。
- 要求:A 的 SLO **不被 B 拖坏**(noisy neighbor),同时 B 的容量最大化。

### 6.2 需求分解

1. **隔离层级选择**:请求级(同副本内优先级,弱)→ 副本级(池隔离,中)→ 节点级(独享,强)。A 有赔付 → **A 至少池隔离**;B 在共享池内做请求级隔离。
2. **B 对 A 的三条侵害路径**:① 抢 batch 槽位(B 的长输出拖步时 → A 的 TPOT p99)② B 的 32K 长 prefill 占 token 预算(A 的 TTFT)③ B 的 KV 挤占(A 的并发 / 触发抢占)。**池隔离一次消掉三条;请求级优先级只能缓解 ①。**
3. 容量是否装得下?——先算账(6.3),**本案的容量结论会推翻"单模型单池"的直觉设计**。

### 6.3 容量估算(Ch3 公式链,70B FP8)

**A 的约束是 decode 并发,不是 prefill 速率**(交互式 = 多轮短输出,请求存活期长):

| 项 | 计算 | 结果 |
|---|---|---|
| A 持续并发 | 50 req/s × 512 tok × 100ms/tok = 50 × 51s | **~2560 并发**(峰值 5120) |
| 单 TP8 副本 decode 并发 | KV 池 60GB ÷ (8.5K tok × 40KB/卡,Ch3 (3-3)) | **~170/副本**(H100) |
| A 需要的 70B 副本 | 2560 / 170 | **~15 副本(持续)~ 30 副本(峰值)** |
| 集群 70B 副本总数 | 64 卡 | **8 副本** |

**结论:64 卡 70B 装不下 A(缺 2×),更装不下 A+B。"把 A 放进 70B 池 + 优先级"的设计在这里不成立**——这是本案的转折点。A 的 prefill 侧(100×8K×(1−0.6 命中) ≈ 320K tok/s 有效需求 ÷ 20K tok/s/副本 ≈ 16 副本当量)同样超预算;两侧都指向同一答案:**A 不能全量走 70B**。

### 6.4 架构设计(参考:模型分层 + 池隔离)

```
64 卡 = A 小池(1 节点,14B FP8,TP1 × 8)+ A 大池(3 节点,70B FP8,TP8 × 3)+ B 池(4 节点,70B FP8,TP8 × 4)
路由(网关,三选一):
  ① 轻量交互(问答/摘要/改写,**输入 ≤4K**)→ A 小池(14B,质量门禁 Ch8 §8.4 交互类任务集)
  ② 重交互(工具调用/长推理/代码)或**输入 >4K** → A 大池(~10-20% 流量,分类器/小模型路由判定;**输入 >4K 必须走 A 大池**,硬边界)
  ③ 批任务 → B 池
A 小池容量:14B GQA(48 层/8 kv heads/128)KV = 192KB/token(FP16)/ 96KB(FP8);8.5K ≈ 1.6GB(FP16)/ 0.8GB(FP8)→ 单卡 decode 并发 ~35(FP16 KV)/ ~70(FP8 KV),8 卡 ≈ 300-560 并发(8.5K 口径;短上下文 1-2K [假设] ≈ 600-1200)→ **只覆盖 A 的短上下文部分(输入 ≤4K),输入 >4K 走 A 大池**
A 大池容量:3 副本 × 170 ≈ 510 并发,承载 A 的 10-20% 重交互(峰值 ~500)✓ 紧
B 池容量:4 副本 × prefill 12-20K tok/s ≈ 50-80K tok/s → B 的 200 req/s × 32K = 6.4M tok/s
        **远装不下 → B 是 best effort:接多少算多少 + 错峰排期 + 排队 30s 超时 shed(6.5)**
KV/调度:
  A 两池:gpu-memory-utilization 0.90,KV 硬上限、不超售、A 之间互不抢占
  B 池:0.88,允许超售 + 内部抢占(LLF,Ch28 B19);超限 429 / 降级(max_tokens 减半)
监控:双租户 SLO burn rate 各一套(双窗口,Ch22 §22.4)+ 每租户 token 归因(Ch23 §23.3)
```

### 6.5 权衡讨论

- **为什么是"模型分层"而不是"纯池隔离"**:容量算账证明 70B 单池撑不起 A 的 decode 并发(差 2×)。隔离解决的是**公平**,分层解决的是**容量**——两者都要,顺序是先用分层把容量账做平,再用池隔离保 SLO。
- **A 小池降级条款(14B 容量是 300-560 @ 8.5K / 600-1200 @ 1-2K,不是无限的)**:路由硬边界 = 输入 >4K 必须走 A 大池;A 小池短上下文并发接近上限(burn rate > 80%)→ 自动收紧阈值(3K→2K,更多 A 流量进 70B);A 大池 burn rate > 50% 持续 10min → 对 A 低价值请求(按任务类型分类)max_tokens 截断——**降级 ≠ 拒绝**(A 有赔付,降级量计入赔付成本模型,Ch23 §23.3)。
- **B 的 200 req/s 不硬接**:best effort 租户的容量是"尽力"不是"承诺"(B 池 4 副本 ≈ 2-4M tok/s/时吞吐,按批任务并发跑,吞吐导向)。业务侧配合削峰(夜间跑批,Ch23 峰谷策略)→ 峰时 B 队列排队,p95 30s 内消化。**被追问"B 的 200 req/s 怎么办"时,这一句是考点。**
- **A 小池的 14B 会不会"质量事故"?**:交互类任务(问答/摘要)对模型规模不敏感(质量门禁用 A 租户的真实任务集,Ch8 §8.4 ②项);重交互走 70B 兜底。**分层路由的判据必须是"任务类型"而不是"请求长度"**(短但难的请求必须能进 70B)。
- **A 大池紧(510 并发 vs 峰值 500)怎么办**:① 路由侧把"重交互"比例从 20% 压到 10%(分类器调阈值,按 A 池 burn rate 自动)② H200 换 A 大池(并发 ×1.76,Ch19 §19.1)③ 极端峰值对 A 低价值请求降级(如 max_tokens 截断,不是拒绝)——**A 有赔付,shed A 是最后手段且要计入赔付成本**。
- **B 池 hot expert(若换 MoE 模型)**:B 的批负载偏斜会放大热 expert → B 池 p99 独立恶化,不传染 A(池隔离);B 池内用案例 8 的治理。
- **借出算力**:A 池空闲**默认不借给 B**(硬边界)。折中 = "B 池排队 > 阈值 且 A 池 KV < 50% 且 A 烧率 < 50% 预算时,B 可进 A 池低优通道(可被 A 随时抢占)"——触发 + 熔断双条件,缺一不启用。

### 6.6 预期追问

1. **A 的流量涨 3× 怎么办?**(A 小池加节点(14B 扩容便宜,DP 零通信)→ A 大池 SLO-aware 扩容(Ch22 §22.4)→ 极端时从 B 池抢节点(gang 迁移,分钟级)→ 最后 shed B 保 A;**顺序:先扩便宜的,最后动赔付池**)
2. **A 大池某节点挂了?**(3→2 副本,−33%;A 重交互 burn rate 升 → 路由阈值自动收紧(更多流量进 14B)+ B 池临时让 1 副本(破例走变更流程,记录事故)——**破例要流程化**)
3. **B 租户投诉"我的 p99 比 A 还高"?**(口径对齐:B 的 SLO 是 30s best effort;B 的 p99 尖刺来自 32K prefill + 热 expert(结构性,加卡不降,Ch28 E24)→ 给 B 的是"削峰排期 + 池扩容",不是"和 A 同延迟")
4. **网关是无状态单点,挂了怎么办?**(多副本 + 健康检查(Ch23 §23.1);shed 决策带租户优先级(A 赔付 > B best effort);网关降级 = 全流量进 A 小池 + 拒绝 B(保赔付租户))

### ◆ 评审点

- [ ] 容量算账**推翻**了"单模型单池 + 优先级"的直觉,且算的是 decode 并发(不是 prefill 速率)
- [ ] "隔离解决公平,分层解决容量" 的分工说清楚
- [ ] B 的 200 req/s 被明确"不硬接"(best effort = 尽力)
- [ ] 借出算力有触发 + 熔断双条件;破例走流程

## 案例 7:128K 上下文 prefill 集群(CP + prefill-only 副本)

### 7.1 需求(带数字)

- 模型:70B 稠密 GQA(80 层,kv_heads=8,head_dim=128),128K 上下文,FP8 权重。
- 场景:深读 / agentic(长文档进、短输出出):峰值 5 req/s,输入 p50 64K / p95 128K,输出平均 512。
- SLO:TTFT p95 < 30s(长任务,松);TPOT p95 < 100ms(decode)。
- 硬件:24 节点(192× H100-80GB)预算 [假设]。

### 7.2 需求分解

1. **prefill 与 decode 的资源画像完全相反**:prefill = 计算重、KV **临时**驻留(传完即释放,池周转快);decode = KV **长期**驻留(128K 请求占 5.12GB/卡(FP16)/ 2.56GB(FP8)到请求结束)。→ **结构上必须分开(prefill-only 池 + decode 池)**,这正是 Ch20 案例 C 的"两级修复"的第二级(结构级)。
2. **128K 是 CP 的"速度选项"而非"容量必需"**:先算 KV 容量(7.3),再决定 CP 深度——与案例 3(1M:MLA KV 修正后,CP 同为吞吐/故障域选项,非容量必需)形成对照,这是面试里区分"套模板"与"算账"的题眼。
3. **传输预算**:128K 的 KV = 5.12GB/分片(TP8,FP16)→ 单链 ~100ms(Ch9 §9.2 表)→ 只占 prefill(~2-3s)的 ~3%;**FP8 + 多链不是容量必需,而是 p99 保护 + NCCL 争抢对策(Ch18 §18.4)**。

### 7.3 容量估算(Ch3 + Ch9 公式回代)

| 项 | 计算 | 结果 |
|---|---|---|
| prefill FLOPs | 2×70e9×128e3 | 1.79×10¹⁶(128K);64K 半量 |
| prefill 单节点 TP8 | 1.79e16 ÷ (8 卡 FP8 有效 ~6e15) | **~3s**(量级;与 Ch9 "8K≈250ms@TP8" ×16 自洽) |
| prefill CP2×TP8(2 节点) | 序列切 2,效率折损 ×1.2-1.3 | **~1.5-2s/条**(组 ~0.5-0.7 req/s,逐条) |
| KV/分片(TP8) | 320KB/token(全模型)× 128K ÷ 8 | **5.12GB/分片(FP16)/ 2.56GB(FP8)** |
| 每 prefill 组并发 | CP2×TP8:KV/卡 = 40.9GB ÷ 16 ≈ 2.56GB(FP16)/ 1.28GB(FP8),池 60GB | **~23(FP16)/ ~46(FP8)条 in-flight/组**(TP8 单节点已有 11/23 条 → **KV 不再是约束,CP 买的是速度**) |
| prefill 池规模 | P 池 = prefill 算力限:5 req/s ÷ ~0.5 req/s/组 | **10 组 CP2×TP8 = 20 节点**(1 组 128K ~1.8-1.9s;10 组 = 2× 故障域余量) |
| decode 单节点并发 | 128K decode:KV 2.56GB/分片(FP8),池 60GB | **~23 条/节点(H100);H200(~116GB 池)→ ~45 条** |
| decode 池规模 | 5 req/s × 512 tok;in-flight ≈ 13/节点([估算]:13 条 in-flight 的步时 ≈ (13×2.56+8.75)GB ÷ 3.35TB/s ≈ 12-13ms,FlashDecoding 必须,Ch11 §11.4) | **2 节点(H100;in-flight 13/节点 ≪ 上限 23 → 不排队,TPOT p95 < 100ms ✓)** |
| KV 传输 | 2.56GB/分片(FP8)× 8 链并行(per-rank 直传) | **~50ms + reshard(见下)** |

**总计:20(prefill)+ 2(decode)= 22 节点 ≤ 24 节点预算**(余量 2 节点 = 增长 + 故障域)。

### 7.4 架构设计(参考)

```
[网关:长度路由(>16K 进本集群)+ 双池队列监控 + 429]
  ├─ P 池(20 节点 = 10 组 CP2×TP8,prefill-only)
  │    Ring CP(跨节点 P2P,与计算重叠,Ch17 §17.2)+ FP8 权重
  │    chunk 8K(激活峰值钳制,Ch21 §21.1)+ 前缀缓存(深读场景文档前缀复用)
  │    传输完成 → KV 立即释放(池周转,不等 decode)
  └─ D 池(2 节点,TP8 × 2;in-flight ≈ 13/节点,H200 为可选余量)
       FlashDecoding split-KV(128K 必须,Ch11 §11.4)+ FP8 KV
       槽位预留 + 队列(Ch9 §9.2 同步协议)
KV 链路:FP8 + 8 链并行 + GDR zero-copy;专用 1-2 口 NIC(与 NCCL 分口,Ch28 D33)
reshard:P 侧 CP2×TP8 → D 侧 TP8:传输前 CP 组内 all-gather 序列维(2 份 P2P,1.28GB/rank(FP8)
       @ ~50GB/s,共 ~0.05-0.1s,与 KV 传输同量级,Ch17 §17.3 痛点的 128K 版)
```

### 7.5 权衡讨论

- **CP2 而不是 CP4/CP8**:128K 的 KV 在 TP8 单节点就装得下(5.12GB/分片 FP16 / 2.56GB FP8 < 60GB 池,单节点已有 11/23 条并发)→ **CP 买的是速度(1.5-2s vs 3s)+ 故障域,不是容量**;CP 深度加倍 = 节点数加倍 + reshard 成本升,TTFT 30s 下不划算。**判断句:128K 的 CP 与 1M 的 CP 都是"吞吐/故障域选项"而非"容量必需"(案例 3,MLA KV 修正后同样成立)——同一机制,KV 修正后两侧容量都有余量。**
- **prefill-only 的价值(必须讲透)**:① KV 传完即释放 → P 池 KV 周转率 ≫ 一体池(一体池的 128K KV 要占 5.12GB(FP16)/ 2.56GB(FP8)每卡到请求结束)② decode 池无 prefill 尖刺 → TPOT p99 干净(Ch20 案例 C 的症状消失)③ P/D 独立扩缩(输入/输出比 125:1,Ch9 §9.3 判据)。**"为什么不是继续调 chunk" = 本案的灵魂追问:chunk 是步级机制,管不了 KV 驻留与扩容不对称两个结构性冲突(B21)。**
- **decode 池的"KV-bound"论证(H200 为可选余量,非成本必需)**:128K decode 并发上限 = 池 ÷ 2.56GB/条(FP8)→ H100 ~23 条/节点,H200(141GB,~116GB 池)~45 条/节点;本案 in-flight 仅 ~13/节点 → **H100 足够,H200 = 2× 故障域余量**(溢价计入案例 4 的 $/M 口径,A16/D34 判据的"值溢价"条件本案不满足)。
- **滑动窗口 decode(若模型支持)**:128K 上下文 decode 只算窗口 32K + sink → KV 1.28GB/分片(32K 窗,FP16)→ 并发 ~47/节点(×4);质量门禁后是**最大的单点杠杆**——但要模型结构支持(Mistral 类),70B GQA 通用模型不支持 → 列为条件项。
- **TTFT 30s 的构成**:排队(<5s)+ prefill(1.5-3s)+ 传输(~0.1-0.2s,含 reshard)+ D 排队(<2s)→ 余量大;**真正的 p99 风险 = 128K 全量 + 长尾排队 + 传输 reshard 抖动**,监控按输入长度分桶报 TTFT(Ch2 A4 口径)。

### 7.6 预期追问

1. **为什么不用一个集群(一体 + chunked prefill)?**(两个结构性冲突:128K 的 KV 驻留挤 decode 并发(5.12GB/条 FP16 / 2.56GB FP8 每卡,一体池 11-23 条并发 + prefill 尖刺挤 decode batch → TPOT p99 劣化)+ 输入/输出比 125:1 的扩缩容不对称;chunk 只解决步时尖刺,不解决 KV 驻留——B21 判据全中)
2. **TTFT 收紧到 10s?**(P 池 10→14-16 组 + CP2→CP4(128K:KV/卡 1.28GB(FP16)/ 0.64GB(FP8),并发 ~46/组,速度 ~0.9-1.2s)+ 前缀缓存预热;再不够 = prefill 池换 H200/B200(FP4 窗口期,compute roof,案例 4 杠杆⑥))
3. **传输失败/超时?**(D 侧槽位释放 + P 侧 KV 作废(白算一次 prefill = P 池超调度成本,案例 5)+ 客户端重试(幂等 + 前缀命中降重试代价,Ch21 §21.4);传输层重试 2 次后丢弃,不阻塞后续请求)
4. **128K decode 为什么必须 FlashDecoding?**(单 CTA 串行扫 128K:大部分 SM 闲着(Ch11 §11.4);split-KV 切 8-16 片并行 + log-sum-exp 归约,正确性 = online softmax 可加性;不切分 → TPOT 直接 ×5-10,100ms SLO 不可能)

### ◆ 评审点

- [ ] "CP 是吞吐/故障域选项而非容量必需" 说清楚(128K 与 1M,KV 修正后两侧容量都有余量,算账为证)
- [ ] prefill-only 的三大价值(KV 周转/decode 池纯净/独立扩缩)对应两个结构性冲突
- [ ] decode 池 KV-bound 论证清晰(并发上限 = 池 ÷ 2.56GB/条;H200 = 可选余量、非成本必需,不是全盘换卡)
- [ ] 传输链路有 FP8 + 多链 + reshard 三件套,失败语义完整

## 案例 8:MoE 热 expert 治理(放置 + 复制 + 请求路由)

### 8.1 需求(带数字)

- 背景:案例 1 的模型 R(235B MoE,128 routed + 1 shared,EP32 × 2 副本),decode batch ~500/副本,TPOT p99 SLO 60ms。
- 症状(监控已抓到):某层 3 个 expert 持续热(M_e 均值 ~31,热 expert ~300,10× 偏斜),出现频率 ~5% 的步 → **p50 正常,p95 抬头,p99 ~3-5× p50**(Ch13 §13.4 量化例同构:偏斜卡 GEMM 10× → 该层 all-to-all 等最慢卡 → 全步放大;MoE GEMM 占 decode 步 ~40% → 热步 ≈ 4-5× 基线步)。
- 要求:不改变模型(训练侧手段不可控),治理到 TPOT p99 < 60ms;给出**分层的治理栈 + 决策顺序 + 每层成本**。

### 8.2 需求分解

1. **先定性:结构性长尾,不是容量问题**(尖刺与负载无强相关、加卡不降频率,Ch28 E24/E27 判据)→ 排除"加卡"答案。
2. **热 expert 的三条后果链**:① 该卡 GEMM 放大(本层)② 下一层 all-to-all 等最慢卡(跨层传播)③ 出现频率 5% → p95 落进热区间(分位数数学)。**治理目标 = 压 ①(单卡 GEMM 时间)与 ③(频率),② 是结果。**
3. **约束**:权重静态(可复制,无一致性成本);路由数据相关(预测有误差);训练侧 router bias 不可控(只能"读结果",Ch16 §16.2)。

### 8.3 治理栈(参考:五层,按成本递增)

| 层 | 手段 | 机制 | 成本 | 预期收益(量级,Ch13/Ch16/Ch26) |
|---|---|---|---|---|
| 0 | **监控(前置,无成本)** | per-expert M_e 直方图(每层×分钟窗)+ per-rank 步时(DCGM)+ all-to-all 完成偏斜 | 指标采集 | 定位热 expert 是治理的前提;"热 5min 持续"触发线 |
| 1 | **静态放置(部署期,一次性)** | 离线跑 router 对目标流量统计热度(Ch13 实验 13.1)→ 热 expert 分散到尽量多卡、同节点 NVLink 域优先、避免双热同卡 | 部署前半天 | **p99 降 30-50%(Ch26 §26.5 量级);必做项** |
| 2 | **动态复制(运行时,分钟级窗)** | 持续热度(非瞬时尖峰)→ 热 expert 复制到 1-2 卡(权重静态 = 纯拷贝,路由表多副本分流)→ 热度回落后释放 | expert 权重 × 副本(235B/129 ≈ 1.8GB/expert,FP8 → 单卡 +1.8GB,极小)+ 路由表变更 | 热步消除 → p95/p99 回落;对"持续热"最有效 |
| 3 | **请求级路由(网关层)** | 副本上报 expert 容量(KV + 热 expert 余量)→ 预测偏斜重的请求路由到富余副本(Ch19 §19.3 MoE 叠加) | 网关状态 + 预测误差(router 数据相关,预测近似) | 削峰(把热摊到多副本),对"突发热"有效 |
| 4 | **capacity + drop(过载兜底)** | expert buffer 溢出 → token 降级走 shared expert(丢 routed 部分)→ 该请求质量降 | 质量(任务级 Δ 必须测,Ch8 §8.4) | 最后手段,过载时才开;触发 = 副本级过载信号 |
| (根) | **训练侧 router bias / aux-loss-free** | 热度分布本身变均匀 | 不在推理团队控制内 | 治本;推理团队"读结果、不能改"(Ch16 §16.2) |

**决策顺序:0 → 1(上线前必做)→ 2(自动触发)→ 3(p99 仍超标)→ 4(过载)→ 向训练侧提热度报告。** 每层开闸条件量化:M_e > 5× 均值持续 5min → 复制;副本 p99 > SLO 80% 持续 15min → 请求路由介入。

### 8.4 架构落地(在案例 1 的集群上)

```
监控面:DCGM per-rank 步时 + 引擎 per-expert M_e(分钟窗直方图)→ Grafana + 告警(热 5× 持续 5min)
放置面:热度统计管线(目标流量离线 router 推理,部署期一次;模型更新/流量画像变更时重跑)
复制面:热 expert 副本注册表(网关 + 引擎共享);复制 = 权重拷贝(静态)+ 路由表版本化;
       释放 = 热度窗口冷却(30min 无 5× 事件)
路由面:副本心跳上报 expert 容量 → 网关软亲和(命中且不过载,Ch19 §19.3)
```

### 8.5 权衡讨论

- **为什么不是"加卡"**:结构性长尾加卡 = 尖刺频率不变、p99 略降、成本翻倍(Ch28 E24 判据);且 EP 扩容收益上限 = min(带宽, 延迟地板, 最热卡 GEMM)(Ch16 §16.4 踩坑框)——**最热卡不解决,加多少卡 p99 都卡在那**。
- **静态放置 vs 动态复制的边界**:静态 = 部署期"已知的热"(可统计);动态 = 运行期"新热的"(统计滞后)。**两者叠加,不是二选一**;统计漂移(业务迭代)→ 重跑离线统计 + 在线 M_e 监控兜底(双保险)。
- **动态复制的一致性为什么便宜**:权重静态(推理期不变)→ 纯拷贝,无同步、无版本号冲突;**模型一旦更新,全部放置/复制作废,重跑**——这是与训练系统复制(需要一致性协议)的本质区别,面试里点一句显功力。
- **请求路由的预测误差**:router 是数据相关(同 expert 分布在不同请求上不同)→ 预测偏斜是近似 → 路由只做"软"偏置(不过载才走),不做硬绑定;**硬绑定 = 把统计误差变成容量误差,更糟**。
- **capacity + drop 的质量门禁**:drop 的 token 走 shared expert → 该请求输出质量降(任务级 Δ 实测,不是 PPL);只允许在"副本级过载 + SLO 燃烧 > 50% 预算"时开,且**按租户分级**(A 租户不 drop,案例 6 的硬边界)。
- **5% 频率的数学(被追问时)**:热步占比 5% → p95 正好落进热区间(p95 = 第 95 百分位,热占 top 5%)→ **热 expert 问题天然先打在 p95/p99,不打在 p50**——这与监控指纹一致,也是"p50 正常但 p99 爆炸"的 MoE 版解释(Ch22 §22.1 第 5 行指纹)。

### 8.6 预期追问

1. **热度统计的流量与线上一致性怎么保证?**(统计用网关真实日志画像重放(Ch2 A8 负载构造),不是合成流量;统计周期 = 流量画像的更新周期(周级)+ 在线 M_e 监控兜底漂移)
2. **热 expert 复制到 2 卡后,all-to-all 模式怎么变?**(路由表里该 expert 有 2 个目标 → token 按副本容量分流(近似轮询/容量比例);dispatch 消息数不变,目标分布变宽 → 单卡 GEMM 时间减半;combine 时 2 份结果按门控归并——**注意:门控是 per-token 选 top-8,复制 expert 不改变"选哪个",只改变"去哪算"**)
3. **复制 + 路由都做完了 p99 还超?** → 说明偏斜 > 5× 且集中(单 expert 独热)→ ④ capacity + drop 评估 + 向训练侧提报告(router bias 是该 expert 的根因);推理侧的天花板 = 复制份数 × 单卡 GEMM,超过就必须训练侧动
4. **为什么不用"每层全 expert 复制"?(= 放弃 EP,退 TP/DP)** 显存:235B expert 全量 × 副本数 ≫ 集群容量;且 EP 的带宽优势消失(每卡 129 expert 全量 = 回到稠密 70B 的显存结构)——**治理目标是"热 expert",不是"所有 expert"**

### ◆ 评审点

- [ ] 先定性"结构性长尾"(排除加卡),再上治理栈
- [ ] 五层栈有**触发条件量化**(5×/5min 等),不是"监控着看看"
- [ ] 静态放置(部署期)与动态复制(运行期)的边界说清,且叠加使用
- [ ] 点出"权重静态 → 复制无一致性成本;模型更新 → 全部作废"的本质
- [ ] 明确推理侧的天花板,知道什么时候必须找训练侧

## 案例 9:推理集群容错(节点挂掉后的语义、恢复时间目标)

### 9.1 需求(带数字)

- 背景:案例 1 的集群(2 副本 × EP32,每副本 4 节点,235B MoE FP8),峰值需求 500 并发,KV 上限 ~1280 并发/副本。
- 要求:① 定义每类故障的**语义**(用户看到什么)② 给出恢复时间目标(MTTR/RTO)③ 算清"挂 1 节点后 SLO 是否仍达标"④ 给出演练计划。

### 9.2 需求分解:故障分类学(按恢复时间递增)

| 故障 | 检测 | 用户语义 | 恢复目标 |
|---|---|---|---|
| 进程崩(单引擎) | watchdog 心跳 5s + NCCL watchdog | 在跑请求中断;客户端幂等重试(网关 request-id 去重)+ 前缀命中 → 重试 prefill 成本减半(Ch21 §21.4) | **MTTR < 2min**(组内自动重启 + 权重重载:235B FP8 ≈ 235GB,存储 ~3-6GB/s → 40-80s + 预热) |
| 节点挂(gang 组) | 心跳丢失 <1min | **整个 EP32 副本挂(4 节点)**;容量 −1 副本;在跑请求 KV 全丢 → 客户端重试(网关限流防重试风暴,Ch23 §23.1) | **RTO < 20min**(检测 <1 + 调度换节点 <5 + 加载预热 5-15,Ch19 §19.2) |
| NVLink 降级/断线 | busbw 漂移 + NCCL 错误日志 + NVLink 错误计数 | 偶发 ×10 尖刺(Ch20 案例 B 指纹)→ 恶化后请求**超时失败而非 hang** | 换线/换卡,分钟-小时;期间该组降权(网关摘流量) |
| IB 口故障 | per-NIC 吞吐告警(Ch23 §23.2) | all-to-all 变慢/超时 → 请求级超时 | 该节点摘出 gang(整组降级) |
| ECC/XID(卡级) | DCGM 告警 | 同节点挂(gang 语义) | 卡隔离 + 节点级恢复 |
| 3× 过载 | 队列深度 + 预测 SLO 违反率 | shed 429 / 降级(Ch22 §22.3) | 自动恢复(burn rate < 0.1% 持续 30min 回缩,Ch19 §19.3) |

**语义设计目标:进程级 MTTR < 客户端重试超时的 1/3**(Ch28 E20);节点级故障窗口(10-20min)**必须显式计入 SLO 设计**(不是"故障时 SLO 暂停",而是"计划内 shed 覆盖恢复窗口")。

### 9.3 SLO 数学(挂 1 节点后还达标吗)

记:单副本 KV 上限 C = 1280 并发,峰值需求 D = 500。

- **设计规则**:正常期目标利用率 ≤80% → N = ⌈D/(0.8C)⌉ = ⌈500/1024⌉ = 1,但**故障域最小 2 副本** → N = 2。
- **挂 1 副本**:容量 C = 1280 vs D = 500 → 利用率 39% → **双 SLO 仍达标**(TPOT 因 batch 集中略升,goodput 曲线在 39% 处近峰值,Ch27 §27.5 方法回代)。
- **需求增长到 D = 900**:N = ⌈900/1024⌉ = 1 → 仍取 2;挂 1 → 900/1280 = 70% → 达标(边缘,goodput 开始回落)。
- **需求增长到 D = 1500**:N = ⌈1500/1024⌉ = 2;挂 1 → 容量 1280 < 1500 → **shed (1500−1280)/1500 ≈ 15%**(长请求先 shed,Ch28 B25)→ TTFT p95 抬头 → **SLO 有损**。
  → **N+1 规则**:设计 N 使 (N−1)·C ≥ 0.8·D_peak → N = ⌈D/(0.8C)⌉ + 1。D=1500 时 N = 3(挂 1 剩 2×1280 = 2560 ≥ 1200 ✓)。
- **夜间 3 副本缩到 1 个副本挂掉(Ch28 D35 追问)**:夜间 D ≈ 30%×500 = 150;N = 3 → 挂 1 剩 2560 容量 vs 需求 150×1.3(突发)= 195 → **SLO 毫无压力(利用率 8%)**——夜间的风险是**成本**不是 SLO;夜间缩容的真正约束 = "扩容前置时间(5-10min)能否追上午间爬升"(Ch22 §22.4 提前量),而不是"挂 1 还扛不扛得住"。

### 9.4 架构与流程设计(参考)

```
感知:  进程 watchdog(5s)+ 节点心跳(30s)+ DCGM/XID + NCCL 错误日志 → 统一告警(端到端 <5min,E21 联动实验)
决策:  网关按副本健康分摘流量(慢副本降权,不硬摘,Ch23 §23.1);P 池订阅 D 池健康
       (D 池降级 → P 池停发新 prefill 给该 D 池,避免白算,案例 5 的槽位机制)
恢复:  进程:组内自动重启(权重重载 + 预热 30-80s)
       节点:K8s gang 整组重调度(N+1 备用节点按整节点计,Ch19 §19.2)→ 容量 N−1 运行
       请求:客户端幂等重试(request-id 去重)+ 前缀缓存降重试成本;流式半输出语义
       = 产品决策(保留已输出段 / 整体重来,计费按保留段)
演练:  季度故障注入(Ch21 §21.4 五类:kill 进程/kill 节点/断 NIC/ECC/3× 过载),
       验证点 = "该故障下的正确行为"(超时而非 hang、shed 生效、告警 <5min),不是"不崩"
```

### 9.5 权衡讨论

- **为什么不能"降级 TP7 / EP31"**:gang 组状态互锁(权重切分 + KV 分片 + 通信拓扑)→ 少一张卡 = 切分不均 + 拓扑残缺 = **整组不可用,降级需要重切权重 = 重新加载,不现实**(Ch14 §14.4/D6)。所以容错的单位是**整节点/整组**,不是单卡。
- **EP64 vs EP32 的故障域代价(回扣案例 1)**:若案例 1 选 1 副本 EP64,挂 1 节点 = **全集群挂**(8 节点 gang);EP32×2 挂 1 节点 = 容量 −50% 且 39% 利用率下 SLO 无损。**案例 1 的"选 EP32×2"一半是容量决策,一半是容错决策——两处要互相引用。**
- **P/D 架构下的故障隔离**:D 池挂 → P 池传输被拒 → P 池 KV 作废(白算成本)→ P 池必须感知 D 池健康(槽位预留机制,案例 5);反之 P 池挂只影响 TTFT,decode 在跑请求不受影响(池隔离的容错红利)。
- **in-flight 语义的责任分层(必须完整说)**:客户端 = 幂等 + 重试策略;网关 = 去重 + 限流重试风暴 + 半输出语义;引擎 = 秒级感知 + 整组重启。**任何一层缺位 = 用户看到"重试风暴把集群打挂"**(重试超时的 1/3 规则反过来:MTTR 超过重试超时 → 重试叠加 → 二次过载,Ch23 §23.1)。
- **RPO = 0 对已完成请求**:流式 token 网关侧落日志(计费 + 审计);in-flight 无 RPO(语义 = 重试)。**别说"数据零丢失"——KV 是无状态缓存,丢了不赔,赔的是体验。**

### 9.6 预期追问

1. **断 NIC 后 TP8 组是"超时失败"还是"hang"?**(默认 NCCL 会 hang → 必须配:NCCL 超时(watchdog)+ 请求级 deadline + 网关超时**级联递减**(引擎 < 网关 < 客户端,Ch21 §21.4 注入③);验收 = 故障注入后"请求以错误返回,集群组被摘出,其余副本正常")
2. **恢复窗口内 SLO 怎么算?**(恢复 10-20min = 计划内容量缺口 → 用 shed 覆盖(先拒长请求)→ SLO 报告里单列"计划内 shed",不计入可用性违约;可用性 99.9% 的 8.8h 预算里**显式预留故障窗口**,Ch19 §19.2)
3. **671B 级(EP64,8 节点 gang)挂 1 节点?**(整 64 卡组挂,Ch28 D19 → 故障域 8 节点 → 需要 ≥2 个完整 64 卡组(DP=2)才有 N+1 语义 → 128 卡起步 → **超大模型的容错成本平方级增长,这是"671B 服务为什么贵"的组成部分**)
4. **怎么防止"重试风暴"?**(网关:per-租户重试预算(令牌桶)+ 429 带 Retry-After + 前缀命中让重试便宜(重试只算未命中段);客户端:指数退避 + jitter;验收 = 3× 过载注入下恢复曲线无二次尖峰)

### ◆ 评审点

- [ ] 故障分类按**恢复时间**分层,每类有检测信号 + 用户语义 + 恢复目标
- [ ] SLO 数学给了公式(N+1 规则)而非"挂了应该没问题"

- [ ] 回扣案例 1(EP32×2 的容错理由)+ 点出 EP64 的故障域代价

| C:B200 D 池(FP4) | P 104(H100)+ D (416/1.9 ≈ 219)×1.3 ≈ 285(B200)≈ **389 卡** | 104×2+285×5 ≈ $1633 | **$0.27** | 生态窗口期 + 价格 2.5× → 当前**不划算** |

**关键结论(反直觉但正确)**:在假设价格下,**硬件代际升级不是本案的成本手段**——H200 的 goodput 增益(~×1.4)追不上 ×1.5 价格;B200 的 ×1.9 追不上 ×2.5。**本案的成本杠杆排序:① 前缀命中 40%→60%(P 池 80→53,−27 卡)② P/D 架构本身(vs 一体池 goodput +20-40%,−80 卡量级)③ FP8(已在基线,vs FP16 −40% 卡)④ 峰谷缩容(夜间 30% 负载 → 夜间缩 40% 卡,混部,−$150-200/时)。** 硬件代际的进入条件(触发器,季度复审):
- H200:价格 ≤1.3× H100,或负载变长上下文(KV-bound,H100 出现并发钳制/OOM shed 时,+76% KV 开始值回)
- B200:价格 ≤1.6× H100,且 FP4 质量门禁通过(Ch8 §8.4 全任务 + 长上下文退化),且 decode 占比上升(输出长度业务变化)
