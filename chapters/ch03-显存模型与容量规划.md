# 第 3 章 显存模型与容量规划

> 难度 ★★★ | 目标 ~25 页 | 前置:Ch1、Ch2
>
> **读完本章你能做什么**
> 1. 把任意推理部署的显存拆成 权重 / KV / 激活 / 开销 四块并分别计算
> 2. 用公式 (3-1)~(3-5) 手算:给定精度下的权重显存、8×H100 能并发多少条 32K 请求、给定流量需要多少卡
> 3. 解释 MoE"显存看总量、算力看激活",以及它对容量规划的含义
> 4. 说清 `gpu-memory-utilization` 实际控制什么
> 5. [进阶] 做 MoE 副本与 KV offload(HBM→CPU→SSD)的容量估算

> **本章定位**:第 1 章给了 KV/token 公式 (1-1),本章把它变成一套可反推、可规划、可面试手算的体系。全书后续所有"要多少卡 / 能并发多少 / P/D 传输多少 KV"的问题都建立在这一章上。

## 3.1 显存的三大块(外加一块)

单卡推理服务的显存预算:

> **显存 = 权重 + KV 池 + 激活 + 框架/CUDA 开销**

- **权重**:固定,模型加载即占满,= P × bytes(3.2 节)
- **KV 池**:服务的"水池",随请求动态进出。现代框架(vLLM/SGLang)启动时一次性预分配整个池,之后按 block 分配/回收(第 5 章)。**显存容量直接决定"并发 × 上下文"的上限**——这是容量规划的主变量
- **激活**:瞬态。decode 时极小(每层 batch × d × bytes,逐层复用);prefill 时是峰值来源——attention 的 O(N²) 中间量若被物化会爆掉显存,FlashAttention 类融合 kernel 正是为消掉它而生(第 11 章)。工程上,激活峰值主要由 **prefill chunk 大小**(`max_num_batched_tokens`)决定
- **开销**:CUDA context、NCCL 通信 buffer(TP 时)、torch caching allocator 的碎片余量,合计 ~1-2GB(多进程部署更高)

**`gpu-memory-utilization`(vLLM 默认 0.9)的真实语义**:框架把显存的 90% 圈为"权重 + KV 池"的总预算,权重装进去之后,**剩余部分全部给 KV 池**。所以它不是"KV 占比",而是"给推理引擎的总预算"。

**例 3-1  70B FP16 TP8 on H100-80G,util = 0.9**

```
总预算        80 × 0.9          = 72 GB
权重(每卡)  140 / 8           ≈ 17.5 GB
开销(NCCL 等)                ≈ 2 GB
KV 池(每卡)  72 − 17.5 − 2    ≈ 52 GB
```

这 52GB 就是该卡能"养"多少请求的全部家底——3.3 节用它反推并发数。util 调低(如 0.7)= 主动缩小 KV 池换碎片余量与 OOM 保险,代价是并发上限(章末自测第 5 题)。

## 3.2 权重大小:精度决定地板

> **权重字节 = P_total × bytes**
>
> bytes:FP16/BF16 = 2;FP8 = 1;INT4 = 0.5 + scale 开销

**例 3-2  70B 模型的权重地板**

| 精度 | 权重体积 | 备注 |
|---|---|---|
| BF16 | 140 GB | 单卡 80G 放不下 → 必须 TP ≥ 2(或量化) |
| FP8 | 70 GB | 单卡 H100-80G 可装下权重,KV 池还有 ~45GB 空间 |
| W4A16(INT4,GPTQ/AWQ) | ~36-38 GB | 0.5B/param + per-group scale(group 128 时 ≈ +1.5-3%)+ 少量 per-channel 元数据 |

两个要点:

1. **量化开销不可忽略但可估算**:INT4 的 scale 按 group(通常 128)存 FP16 → 每 128 个参数多 2 字节,占比 ≈ 2/128/0.5 ≈ 3%;FP8 的 per-tensor / per-block scale 近零。**"4bit = 体积除以 4"是错的,是"除以 4 再加 3-5%"**。
2. **100B+ 稠密模型的现实**:BF16 下 100B = 200GB → 至少 3 张 H100-80G;FP8 下 100GB → 2 张。加上 KV 池需求,实际部署普遍 TP4/TP8——量化与并行在这里第一次汇合。

**MoE 的特殊性(本章关键)**。一句话定义:**MoE(Mixture of Experts)= 每层 FFN 不是一个矩阵,而是一组"expert"(小 FFN),token 经轻量 router 选 top-k(常 1-8)个 expert 通过**——所以"总参数"(全部 expert,定显存)与"激活参数"(单 token 实际走过的,定算力)是两回事:

> **显存看总参数,算力看激活参数。**

DeepSeek-V3:671B 总参数、37B 激活(top-8 expert)。含义:

- **显存**:所有 expert 必须常驻(路由是数据相关的,任何 expert 都可能在下一秒被选到)→ FP16 需 1.34TB、FP8 需 671GB。8×H100-80G(640GB 可用)装不下 FP8 全量 → **必须 EP 跨机、PP,或 offload**——模型"放不下"不是 bug,是架构决定的
- **算力**:每 token 只过 1 个 shared expert + 8 个 routed expert ≈ 37B 的 GEMM 量 → TPOT 可以接近一个 37B 稠密模型

这正是 MoE 商业价值的物理来源:**用 671B 的显存,买 37B 的延迟 + 接近超大模型的容量**(第 13、16 章展开)。容量规划时,这个"显存/算力解耦"必须写进公式——3.4 节。

## 3.3 KV Cache 精算:从 token 到并发数

复用第 1 章公式,补上反推方向:

> **(3-1)  KV / token = 2 × L × h_kv × d_head × bytes**(公式 1-1,此处沿用编号体系)
>
> **(3-2)  单请求 KV = (KV/token) × n_ctx**(n_ctx = prompt + 输出,按最大上下文预留)
>
> **(3-3)  每卡可并发 = KV 池(每卡) ÷ 单请求每卡 KV,向下取整**

**例 3-3  8×H100-80G 跑 Llama-3 70B(TP8、BF16),32K 上下文能并发多少?**

```
KV/token(全请求)   = 2 × 80 × 8 × 128 × 2B        = 320 KB
TP8 下每卡承担 1/8  = 40 KB/token
单请求 32K(32768 token)每卡 = 32768 × 40KB ≈ 1.28 GB
并发数 = 52 GB ÷ 1.28 GB ≈ 40 个请求
```

即:该集群稳态最多"养"约 40 条 32K 并发请求,总 KV ≈ 40 × 10GB ≈ 400GB(8 卡合计)。

**变量敏感性(面试手算三连)**:

| 改动 | 并发数变化 | 机制 |
|---|---|---|
| KV 改 FP8 | ×2 | bytes 2→1,公式 (3-1) 直接减半(第 8 章:近无损) |
| 模型换 MHA(h_kv=64) | ÷8 | h_kv 8→64 |
| sliding window 8K(模型支持时) | 32K→8K,×4 | 长上下文的 KV 只保留窗口(第 11 章) |
| 上下文 32K→128K | ÷4 | n_ctx 线性 |

> **面试陷阱框:手算并发数的三个漏项**
> 1. 忘除 TP:单请求 KV 是摊到 TP 张卡上的,每卡只算 1/TP;
> 2. 用"总显存"当 KV 池:必须减掉权重与开销(例 3-1 的 52GB,不是 80GB);
> 3. 忘 prefill/decode 共用一个池:一条 128K prefill 中的请求会暂时"占用"远超其最终 decode 所需的池空间(chunk 调度后释放,第 6 章),高并发下长请求会挤掉短请求。

## 3.4 容量规划方法:从流量到卡数

> **(3-4)  需求吞吐 = λ × L_out**(λ = 请求到达率 req/s,L_out = 平均输出长度)
>
> **(3-5)  TP 组数 = ⌈需求吞吐 ÷ 单组 goodput⌉ × 余量(1.3~1.5);卡数 = TP 组数 × TP size**

关键点:**单组 goodput 不手算,实测**(第 2 章 goodput 曲线的 knee 点)。这是"为什么第 2 章在第 3 章之前"的原因——容量公式的输入是测量,不是理论值。

**例 3-4  一次完整的容量规划(数字为示意,用于演示流程)**

需求:λ = 20 req/s,平均输出 L_out = 512 token,SLO:p95 TTFT < 2s、p95 TPOT < 50ms。模型 70B FP8,TP4(H100-80G)。

```
需求吞吐        = 20 × 512 = 10,240 tokens/s
单组 goodput    = 2,600 tokens/s(实测,第 2 章口径)
TP 组数         = ⌈10240 / 2600⌉ = 4
× 余量 1.4      = 5.6 → 取 6 组
卡数            = 6 × 4 = 24 × H100
```

余量买的是什么:**突发吸收 + SLO 余量 + 硬件故障**(一张卡挂 = 整个 TP 组下线,gang 调度下的故障域,第 19 章)。余量取 1.3 还是 1.5 取决于业务对"降一级 SLO"的容忍度(第 22 章)。

**preemption / swap 在容量中的角色**:KV 池满时,调度器可以抢占(第 6 章):

- **recompute**:被抢请求的 KV 丢弃,重跑 prefill——容量"变大"了(池可以超售),代价是重算 O(N²) 计算,p99 恶化
- **swap**:KV 换出到 CPU DRAM——重入时换回,代价 ≈ 单请求 KV / DRAM 带宽(32K 请求 ~10GB ÷ 50GB/s ≈ 200ms/次)

所以严格说,**容量 = 硬容量(3-3)+ 可超售容量(抢占策略决定的)**。超售换容量、毁尾延迟——这个权衡是第 21 章 OOM 治理的入口。

**MoE 容量规划(3.2 的落地)**:

- 卡数由**总参数**决定(例:671B FP8 ≈ 671GB 权重 + KV 池 → 至少 8 卡 80G 才够权重,EP 跨机扩)
- TPOT 预期按**激活参数**(37B)对照稠密基线
- 热 expert 副本(第 16 章)会额外占显存:副本数 × 单 expert 权重要从 KV 池预算里扣掉
- 结论模板:"N 张卡装模型,goodput 对标 ~37B 稠密,余量按 X"——三句话就是面试里 MoE 容量规划的标准答案

## 3.5 [进阶] KV offload:把容量从 HBM 延伸到主机与磁盘

分级存储与带宽(量级):

| 层级 | 带宽量级 | 容量 | 用途 |
|---|---|---|---|
| HBM | 3-8 TB/s | 80-180 GB/卡 | 热 KV(当前 decode) |
| CPU DRAM | 50-100 GB/s(双路) | TB 级 | 温 KV(swap、前缀复用) |
| NVMe/SSD | 1-7 GB/s | 10TB+ | 冷 KV(跨会话、跨副本复用) |

估算方法:

- **swap 型 offload**(preemption 换出):有效并发 ≈ HBM 并发 + 可换出队列;但每次换入时间 = KV/DRAM 带宽(例 3-3 的 32K 请求 ≈ 200ms),**只适合低频长尾请求**,不适合主流量
- **跨副本复用**(LMCache 类):同一前缀在不同副本命中时,从远端 KV 存储拉取而非重算 prefill——引入"全局并发"概念:集群级前缀命中率为 HBM 节省的 prefill 计算 = 命中率 × prefill 成本(RAG 场景收益最大,第 5 章)
- **经验法则**:offload 是**扩容量**的工具,不是**降延迟**的工具;用它之前先确认瓶颈是"池不够"而不是"调度/通信"

> 常见误用:把 offload 当"长上下文加速方案"——128K 请求的 KV 换入换出本身就是 200ms 级,远小于 prefill 重算(秒级)的节省,但对 TTFT SLO 极敏感的场景是负优化。先测,再上。
