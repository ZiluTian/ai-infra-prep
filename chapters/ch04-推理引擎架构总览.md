## 4.1 请求生命周期:三个引擎共用的骨架

无论哪个框架,一条请求的旅程都是六段。先记住骨架,4.2-4.4 再展开"每段在每个框架里由谁做、怎么做得快":

```
HTTP 请求 ──① API层──► 引擎队列 ──② 调度──► ③ 执行(GPU forward)
   ▲                                                    │
   │ SSE 流式回传  ◄──⑥ detokenize── ⑤ 状态更新/停检 ◄──┘
```

**① API 层(独立进程,CPU)**
- 协议解析(OpenAI Chat/Completions)、鉴权限流(网关职责,serving 框架也各有一层)
- **chat template + tokenize**:这是推理的第一个"隐形成本"——模板渲染与 batch tokenize 在 CPU 上,高并发时它能成为瓶颈(第 20 章"GPU 闲但 CPU 满"案例的源头之一)
- 产出:Request 对象(id、prompt_token_ids、sampling_params:temperature/top_p/max_tokens/stop、priority)

**② 调度(引擎之心,CPU,每 iteration 一次)**
- 以 iteration(一次 forward 步)为粒度决策:本步放哪些请求、各给多少 prefill token、多少 decode token、是否抢占
- 产出 "batch 计划":(请求列表, 每请求 token 数, KV block 映射)
- 第 6 章的全部内容(continuous batching / chunked prefill / 抢占)都发生在这里

**③ 执行(GPU,ModelRunner)**
- 把 batch 计划组装成张量:input_ids、positions、**block_table(物理 block 映射,第 5 章的产物)**
- 选择执行路径:decode 步 → CUDA graph 回放(按 batch size 分桶);prefill / 混合 → eager(变长)
- 模型 N 层 forward(含 TP/EP 通信,第 15/16 章)+ 采样(temperature/top-p/top-k)

**④→⑤ 状态更新与停检(CPU,调度器内)**
- token 入队、block table 推进、停检(EOS / max_tokens / stop string)
- 结束请求:释放 KV block(前缀共享时只减引用计数,第 5 章)

**⑥ 输出(CPU,增量)**
- 增量 detokenize(按字节流式;注意 UTF-8 多字节字符跨步切分)
- SSE 回传;客户端"首 token"时刻即 TTFT 的测量点(第 2 章)

**两个进程问题(面试追问常客)**:

1. **调度器跑在哪?** CPU 进程。高并发下"CPU 调度速度必须追得上 GPU 执行速度"是硬约束——SGLang 的 overlap 调度(4.3)就是为此而生。
2. **tokenize 跑在哪?** API 进程,与 GPU 解耦。这正是 vLLM v1 双进程设计(4.2)把 API 层独立出去的动机之一。

> **案例框:冷启动的第一个 100ms 花在哪**
> 冷启动 = 引擎初始化(CUDA context、NCCL init、权重加载、CUDA graph 捕获、KV 池预分配)+ 首请求(JIT 编译、前缀缓存全冷)。70B TP8 的冷启动常见 1-3 分钟,首请求 TTFT 可达稳态的 10-100 倍。生产扩容必须把"预热"纳入部署流程(第 23 章),而不是当成框架 bug。

## 4.2 vLLM v1:主线源码走读

### 4.2.1 为什么 v0 要重写

v0(2023-2024)是单进程架构:API handler、调度器、模型执行器同进程(每 TP rank 一进程),线程 + ZMQ 连接。它证明了 PagedAttention + continuous batching 的价值,也留下了三个结构性问题:

1. **GIL 与异步**:调度、tokenize、流式输出、指标日志全抢 GIL,并发越高 CPU 路径越差
2. **调度与执行耦合**:调度器必须"等 GPU 跑完"才能决定下一步,CPU 决策时间与 GPU 执行严格串行 → CPU 调度耗时直接变成 GPU 空转
3. **扩展点缺失**:P/D 分离(第 9 章)、分布式 KV、多模态、async LoRA 都需要"第二个进程承载状态",单进程结构改不动

v1 的答案:**状态与计算拆成两个(多个)进程,中间用消息**。

### 4.2.2 组件清单

```
┌────────────────────────────┐         ┌───────────────────────────────────┐
│ API server 进程 (frontend)  │  MP/    │ EngineCore 进程                   │
│ • OpenAI 协议 / SSE 流式    │  ZMQ    │ • Scheduler(v1/core/sched/       │
│ • tokenize / detokenize    │◄───────►  scheduler.py)                     │
│ • 客户端视角的请求状态       │  消息    │ • KVCacheManager + BlockPool      │
└────────────────────────────┘         │   (v1/core/kv_cache_manager.py)   │
                                       │ • ModelExecutor(v1/executor/*)    │
                                       │   └ 每 TP rank: GPUModelRunner    │
                                       │      (v1/worker/gpu_model_runner) │
                                       │ • Sampler / Speculator            │
                                       └───────────────────────────────────┘
```

- **API server(frontend)**:协议、tokenize、流式、客户端状态。不感知 KV。
- **EngineCore**:一切"推理状态"的家:调度器、KV block 池、请求执行态。每 iteration 主循环在这里。
- **GPUModelRunner**:每个 TP rank 一个,收"执行指令"(batch 计划 + block table),回 logits(每位置对词表的未归一化分数,采样输入)/ 采样 token。
- 进程间消息传的是**指令与结果,不是 KV**——KV 在 GPU 上,调度器只操作 block 号。

> **v1 的关键设计点:调度器只操纵整数(block id),不碰字节(KV 内容)**。这个解耦让 KV 传输层(NIXL:NVIDIA 开源的 GPU↔GPU KV/权重搬运库,RDMA 零拷贝,第 9 章)能以"block 搬运工"身份插进 P/D 分离架构,而不需要动调度器。

### 4.2.3 每步主循环(调度器核心)

v1 调度器每个 iteration 做(伪代码;文件级定位见 4.2.4 代码地图):

```
loop:
 1. 预算:本步 token 预算 = max_num_batched_tokens(默认 2048,v0.32.0 基线;附录 G)
    —— prefill chunk 与 decode token 共享这一份预算
 2. 先排 running 请求(decode,每请求 1 token):
    - block 不够 → 抢占:recompute(丢 KV 回 waiting)或 swap(第 6 章)
 3. 再排 waiting 队列:
    - 短 prompt 整段 prefill;长 prompt 取一个 chunk(chunked prefill)
    - 前缀命中:命中前缀的 block 直接"收养"(引用计数 +1),
      只把未命中部分计入 prefill 预算
 4. 组装 batch:prefill + decode 混合(v1 同一 forward 可共存)
 5. 执行指令 → ModelExecutor → 各 rank 的 ModelRunner
 6. [v1 异步调度] GPU 跑第 n 步时,CPU 提前排第 n+1 步
```

三个值得停下来的点:

1. **token 预算(`max_num_batched_tokens`)是 v1 的总阀门**:它同时限制 prefill chunk 大小与 decode 数量,决定每步 prefill/decode 比例 → 直接决定 TTFT/TPOT 的权衡曲线形状(第 6 章围绕它展开)。
2. **前缀缓存 = block 哈希 + 复用**:prefill 前查 block 哈希(带父链),命中 block 被收养、对应 token 不占 prefill 预算——命中越多 TTFT 越低(第 5 章定量)。
3. **CUDA graph 分桶**:decode batch 按 batch size 桶(如 1,2,4,…,128)捕获 graph,运行选 ≥ 当前 batch 的最近桶,不足部分 pad(pad 的 token 结果丢弃)。变长的 prefill/混合 batch 一般走 eager。padding 开销与 graph 机制本身在第 12 章细讲。

### 4.2.4 代码地图(断点打在哪)

| 关注点 | 文件(v1) |
|---|---|
| 调度主循环 / 预算 / 抢占 | `vllm/v1/core/sched/scheduler.py` |
| block 池 / 前缀哈希 / 收养 | `vllm/v1/core/kv_cache_manager.py` |

## 4.3 SGLang:RadixAttention 与零开销调度

SGLang(SRT,Structured Generation Language;NSDI'24)的架构组件与 vLLM 同构——TokenizerManager(API)、Scheduler(CPU 事件循环)、ModelRunner(每 GPU)、DetokenizerManager,ZMQ 通信。差异全在**两个设计**:

**1. RadixCache:显式基数树管理 KV 复用**

- 节点 = block 对齐的变长 token 序列;边 = 后续分叉
- `match_prefix(tokens)`:下行求最长匹配前缀 → 命中部分直接复用,零 prefill
- `cache_finished_req`:请求结束时整条路径插入树(ref++)
- 逐出:叶子 LRU,可整棵子树逐出(尊重 refcount)
- 与 vLLM 的"定长 block + 哈希表"相比:

| | vLLM(哈希 block 池) | SGLang(radix tree) |
|---|---|---|
| 数据结构 | 固定 16-token block + hash(含父链) | 变长节点基数树 |
| 命中条件 | 按 block 粒度前缀对齐 | 任意长度前缀,天然支持分叉 |
| 逐出 | 单 block LRU | 子树 LRU |
| 甜区负载 | 通用(共享 system prompt) | 多轮对话、few-shot、tree-of-thought/多候选、agent 循环(共享主干、分叉探索) |

两者目标相同:**用复用消灭重复 prefill**;差别是"能表达多细的复用"。论文报告:高复用负载下端到端最高 ~2-6×(负载相关,复测为准)。

**2. overlap(零开销)调度**

GPU 执行第 n 步 batch 的同时,CPU 完成第 n+1 步的 调度 + 输入组装(block table、CUDA graph 选择)。隐藏的是 CPU 调度/组装耗时(通常每步 ~ms 级)——高并发下 CPU 时间直接变成 GPU 空转,vLLM v1 的异步调度(4.2.3 第 6 步)解决同一问题,两边机制相近、实现细节不同。

**其他值得知道的 SGLang 特性**:
- 结构化输出:压缩 FSM(基于 xgrammar 类),约束解码零额外 CPU 往返
- 投机解码:EAGLE 等,与 overlap 调度协同
- PD 分离:与 Mooncake 传输引擎集成的 disaggregated prefill(第 9 章)

源码定位:`sglang/srt/managers/scheduler.py`(事件循环)、`sglang/srt/mem_cache/radix_cache.py`(RadixCache:match_prefix / cache_finished_req / 逐出)、`sglang/srt/model_executor/model_runner.py`。

## 4.4 TensorRT-LLM:编译式路径

与前两个"解释执行"的引擎不同,TRT-LLM 是 **AOT 编译 + 运行时执行**:

1. **构建期**:模型定义 + 配置(TP、精度、KV block size、插件)→ 编译出 engine(序列化 plan 文件)。LLM 特有的算子(带 paged KV 的融合 attention、fused MoE、采样)以优化实现 / C++ plugin 形式进入图
2. **运行期**:executor(Python API)加载 engine,in-flight batching(TRT-LLM 对 continuous batching 的叫法:新请求中途即可加入,不必等 batch 集满,Ch6)在每个 iteration 组 batch(上限 `max_batch_size`),KV 按 block 预分配,支持 **APC(automatic prefix caching)** 的 block 复用与 host offload(KV 换出主机内存)

含义与代价:

- **性能上限高**:图级优化空间大(kernel 选择、通信重叠、warp(GPU 上 32 线程一组,kernel 调度基本单元)级调优都可在构建期固化),同模型同硬件上常有小幅领先
- **模型/配置绑定**:engine 是"模型 × 配置"的产物——**换模型架构、换 TP、换精度都要重编译**;新模型架构支持节奏慢于解释式引擎(社区引擎常随发版即支持,TRT-LLM 要等官方适配)
- **精度格式**:FP8(权重+激活)、INT8 SmoothQuant、INT4/INT8-AWQ;Blackwell 上 NVFP4
- **开发面**:C++ plugin 生态强,Python 层灵活性弱;调试链路长(engine 是黑盒序列化文件)
- 生态位:NVIDIA 全家桶(NIM 微服务即基于 TRT-LLM)、边缘(Jetson)是它的独占领地

## 4.5 对比与选型

| 维度 | vLLM(v1) | SGLang | TensorRT-LLM |
|---|---|---|---|
| 执行模型 | 解释式,双进程引擎 | 解释式,事件循环 + overlap | AOT 编译 + in-flight batching |
| KV 复用 | 定长 block + 哈希前缀缓存 | radix tree(RadixAttention) | APC block 复用 |
| 调度特色 | 统一 token 预算、异步调度 | 零开销调度、cache-aware 路由 | 运行时 batch 上限、host offload |
| 投机解码 | draft 模型 / EAGLE / Medusa 类 | EAGLE 类,与 overlap 协同 | lookahead / draft-target |
| MoE | fused_moe + EP(DeepEP 集成) | EP + DeepEP | wide expert + fused MoE + EP |
| 量化覆盖 | 最广(GPTQ/AWQ/FP8/…) | 广(AWQ/GPTQ/FP8) | FP8 / INT8-AWQ / INT4-AWQ / NVFP4 |
| 二次开发 | Python 插件面、LoRA、社区热 | Python(SRT),迭代快 | C++ plugin,门槛高 |
| 新模型支持 | 快(社区) | 快 | 慢(官方适配节奏) |
| 生态 | 社区最大,事实标准 | 研究友好、结构化生成 | NVIDIA 栈、NIM、边缘 |

**选型决策(面试可直接背的三条)**:

1. **默认 vLLM**:社区最大、特性迭代最快、踩坑资料最多;性能同档时,选维护风险最低的
2. **高前缀复用 / 结构化输出 / 多候选分叉负载 → SGLang**:radix tree 与约束解码是结构性优势,不是参数调出来的
3. **模型集固定 + 追求极限性能 + C++ 团队 + NVIDIA 全栈(含边缘)→ TRT-LLM**:编译期固化换运行期上限

> 重要提醒:选型不是一次性决定。**每一代新模型出来,三家的支持速度与优化深度都会重新洗牌**——"上一代选 TRT-LLM,这一代先跑社区引擎"是常态。选型结论必须带"截至哪个版本"的注脚(附录 G)。
