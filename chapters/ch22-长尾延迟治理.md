## 22.1 长尾来源清单(含指纹)

| 来源 | 机制 | 指纹(在指标里长什么样) |
|---|---|---|
| **抢占重算** | KV 被抢占,重新 prefill | 个别请求总时长 ≫ 同长度正常请求;`num_preempted` 与尖刺时刻对齐 |
| **长 prefill 阻塞** | 大 chunk prefill 占步时间 | 尖刺**成批出现**(同一步里所有 decode 请求一起慢);TTFT 同时恶化 |
| **通信 straggler** | NVLink 降级 / PFC / 热 expert 卡(Ch16/18) | p99 点状、**无负载相关性**(轻载也尖刺);NCCL 段偶发 ×10 |
| **clock/power throttle** | 温度/功耗墙降频(Ch20 DCGM) | 尖刺**同时刻全副本**(机房散热/电力事件);DCGM throttle 原因非空 |
| **GC/调度停顿** | CPU 侧长停顿(tokenize 大文本、python GC) | GPU 大 gap + CPU 活动;与"大 prompt 请求"相关 |
| **MoE 热 expert** | 热 expert 卡 M_e 偏斜(Ch13/16) | **MoE 特有**:尖刺频率 ∝ 热 expert 出现频率;p50 完全正常 |
| **prefix cache 逐出** | 热前缀被 LRU 逐出,重算 prefill | TTFT 尖刺与"前缀热度波动"相关;命中率骤降时刻对齐 |

**用法**:p99 异常 → 先分"突刺型(点状)"还是"慢性长尾(面状)"(22.2),再按指纹对号入座。**突刺型先查硬件/事件(通信、throttle),慢性型先查负载结构(长请求占比、热 expert、抢占)**。

## 22.2 p99 定位方法

**每请求 trace(数据基础)**:vLLM `log_stats` / SGLang 调度日志给出每请求的:入队时刻、排队时长、prefill 时长、decode 步序列、完成时刻。**p99 定位 = 找出 p99 的那批请求,逐段与正常请求对比**。

**时间对齐法(核心技巧)**:

```
时间轴:  [系统事件日志: NCCL 错误/throttle/抢占/扩容/发布]
          [每请求分段: 排队 | prefill | decode 步时直方图]
          [全局: p99 时刻]
→ 尖刺时刻 ±5s 内,哪个事件/哪段异常?
```

**两个分布判读**:

- **p99/p50 比值时序**:比值稳定 1.5-2× = 正常长尾;比值周期性放大 = 周期性事件(发布、GC、批量导入);比值持续爬升 = 慢性问题(碎片、热 expert 累积、配置退化)
- **尖刺的"波及面"**:一条请求尖刺 = 请求级(长 prefill/抢占);**同一步所有请求一起尖刺 = 系统级(通信/throttle/大 prefill 入步)**——这个区分一次定位就把范围砍半

## 22.3 缓解 playbook(三档,按成本递增)

**架构级(解决"结构性长尾")**:

1. **chunked prefill + P/D**(Ch6/Ch9):长 prefill 不再独占步 → 消除"成批尖刺"的第一档;判据满足时上 P/D(结构级)
2. **长请求分流**:输入 > 阈值(如 64K)的请求路由到 prefill 集群 / 独立副本(Ch17 §17.3)——**把"最慢的一类请求"物理隔离**
3. **副本隔离(热请求/噪音前缀)**:高频重复前缀(批量任务)单独副本池,避免其 prefill 风暴污染通用池(Ch19 §19.3 的软亲和变体)

**调度级(解决"顺序不公平")**:

- **deadline-aware 调度**(EDF/LLF):按"剩余生成时间 vs SLO deadline"排序,快完成的优先 → 保护 p99 的"短请求"不被长请求压住
- 代价:长请求的公平性受损 → 用"优先级池"(Ch29 案例 6)隔离,而不是全局 EDF
- **抢占阈值调优**:KV 压力到 X% 才开始抢占(而非 100%),给 decode 留缓冲(Ch21)

**过载级(解决"容量不够"的长尾)**:

- **shed 决策器**:队列深度 + 请求预测耗时(输入长度 → prefill 时间估算)→ 超 SLO 预算的请求**拒绝(429)或降级**(降 max_tokens / 换小模型)
- 原则:**宁可拒绝 1%,不让 99% 慢**——p99 SLO 的数学含义
- **SLO 预算传导**:网关层就按"副本剩余 SLO 预算"分流(哪个副本还能在 deadline 内完成,去哪个)

**MoE 专项(Ch16 §16.3 的长尾视角)**:热 expert 复制(显存换 p99)+ 请求级路由(副本容量上报)。**决策量化:复制热 expert 的代价 = 权重 × 副本数 × 卡数;p99 收益 = straggler 步消除比例——用 22.2 的尖刺频率 × 尖刺幅度估算收益**。

## 22.4 SLO 工程

**SLO 定义(示例,必须带数字)**:

```
p95 TTFT < 2s(输入 ≤ 8K 分位)  |  p99 TPOT < 100ms  |  可用性 99.9%(月度)
分租户: 高优池 p95 TTFT < 800ms(独享副本), 普通池 p95 TTFT < 2s
```

**SLO burn rate(告警设计,Google SRE 口径)**:

- 燃烧率 = SLO 违反速率 / 预算速率(如 5 分钟内烧掉月度预算的 5% = 快速燃烧)
- 双窗口告警:**快速燃烧(5min 窗,5%)→ 页人(P1);慢速燃烧(1h 窗,0.9%)→ 工单(P2)**
- 比"固定阈值告警"好在哪:**阈值告警在负载变化时误报/漏报;burn rate 自适应容量**——容量翻倍后,p99 同样恶化烧预算的速度不同,阈值型告警要重调,burn rate 不用

**SLO-aware 扩容(Ch19 §19.3 的深化)**:

- 信号:不是"队列深度"(滞后)而是 **预测 SLO 违反率**——队列深度 × 平均剩余时长 vs SLO 预算
- 提前量:扩容前置时间(模型加载 ~分钟级,Ch19)→ **在队列爆之前 N 分钟触发**,N = 前置时间 × 2
- 回缩:burn rate < 0.1% 持续 30min 才缩(防锯齿)

> **面试陷阱框:"p99 高,加卡就行"**
> 先问:长尾是**结构性**(热 expert/长 prefill/通信)还是**容量性**(排队)?结构性问题加卡 = p99 略降但根因还在(尖刺频率不变),成本翻倍。**22.1 的指纹先做,加卡是最后的手段,且只对"容量型长尾"有效。**
